# `PATCH api/receipts/{id}` — решение модератора по чеку (CRM-бэк)

> Не путать с эндпоинтом промо-инстанса `PATCH /api/v1/crm/receipts/{id}` (§2.14 свода CRM API): тот принимает решение со стороны CRM. Ниже — контракт панели управления с CRM-бэком; маппинг на канал инстанса — в §7.

## 1. Назначение и место во флоу

Эндпоинт применяет решение модератора к чеку, который хранится в CRM-бэке (чек забран с промо-инстанса на модерацию). Это единственный способ сменить статус модерации и флаги акционности позиций из панели. После применения CRM-бэк передаёт решение на промо-инстанс (§7).

Фото чека эндпоинт не принимает и не отдаёт (панель берёт снимки из отдельного источника по ID чека). Данных участника, кроме `user_id`, в CRM нет — в контракте их нет.

## 2. Запрос

Формат — легаси CRM-бэка: `Authorization: Bearer {token}` панели, тело JSON, ответ в конверте `{success, message, error}`.

**Путь:** `id` — внутренний числовой ID чека в CRM (тот же, что `id` ряда в списке).

**Тело:**

| Поле                | Тип    | Обяз.          | Описание                                                                    |
| ------------------- | ------ | -------------- | --------------------------------------------------------------------------- |
| `moderation_status` | string | да             | Решение модератора (словарь §3.1)                                           |
| `decline_reason`    | string | при `rejected` | Код причины отказа (словарь §3.2)                                           |
| `comment`           | string | нет            | Комментарий модератора                                                      |
| `retail_chain_id`   | number | нет            | Уточнение торговой сети (из справочника `retail_chains` детальной карточки) |
| `products`          | array  | нет            | Правки акционности позиций: `{gtin, is_promo}`                              |

`products[]`:

| Поле       | Тип    | Описание                       |
| ---------- | ------ | ------------------------------ |
| `gtin`     | string | Ключ позиции в составе чека    |
| `is_promo` | bool   | Новый флаг акционности позиции |

Сопоставление позиций — по `gtin`; неуказанные позиции не меняются. Неизвестный `gtin` → `422 VALIDATION_ERROR` с полем `products`.

## 3. Словари

### 3.1. `moderation_status`

| Код          | Русское имя  | Смысл решения                          |
| ------------ | ------------ | -------------------------------------- |
| `pending`    | На модерации | Возврат чека в очередь модерации       |
| `approved`   | Одобрен      | Чек принят                             |
| `rejected`   | Отклонен     | Чек отклонён (терминально)             |
| `suspended`  | Отложен      | Решение отложено                       |
| `need_photo` | Запрос фото  | Запрос у участника дополнительных фото |

### 3.2. `decline_reason`

| Код           | Русское имя                              |
| ------------- | ---------------------------------------- |
| `WRONG_CHECK` | Чек некорректен                          |
| `NO_PRODUCT`  | Отсутствует акционная продукция          |
| `BAD_PHOTO`   | Фото нечитаемо или не соответствует чеку |
| `DUPLICATE`   | Дубликат                                 |
| `OTHER`       | Другое                                   |

## 4. Правила применения

### 4.1. Допустимые переходы статуса

| Текущий статус | Разрешённые решения                               |
| -------------- | ------------------------------------------------- |
| `pending`      | `approved`, `rejected`, `suspended`, `need_photo` |
| `suspended`    | `pending`, `approved`, `rejected`                 |
| `need_photo`   | `pending` (возврат на модерацию)                  |
| `approved`     | `rejected` (откат ранее принятого чека)           |
| `rejected`     | — терминальный, любой запрос → `422`              |

Недопустимый переход → `422 VALIDATION_ERROR` с полем `moderation_status`.

### 4.2. Окно правки состава и сети

`products` и `retail_chain_id` принимаются, пока текущий статус чека — `pending`, `suspended`, `need_photo`, а также в запросе, которым делается откат `approved → rejected`. На чеке в `rejected` запрос отклоняется целиком. После `approved` флаги правятся только одновременно с откатом решения.

### 4.3. Статусы продуктов — выводные, не принимаются

Поле статуса продукта в запросе отсутствует: статус выводится из статуса чека и флага `is_promo` (модель промо-инстанса, 9.4 §8):

| Статус чека                            | `is_promo` | Статус продукта                            |
| -------------------------------------- | ---------- | ------------------------------------------ |
| `approved`                             | `true`     | `CONFIRMED`                                |
| `approved`                             | `false`    | `CANCELLED`                                |
| `rejected`                             | любой      | `CANCELLED` (флаг сохраняется как история) |
| `pending` / `suspended` / `need_photo` | любой      | `PENDING`                                  |

Модератор на странице двигает только чекбокс `is_promo`; колонка статуса в таблице продукции — читаемое следствие.

### 4.4. Прочее

- Повторный запрос с тем же `moderation_status` — не ошибка (идемпотентное решение), но и не событие: письмо участнику повторно не инициируется.
- `decline_reason` без `rejected` игнорируется; `rejected` без `decline_reason` → `422 VALIDATION_ERROR` с полем `decline_reason`.

## 5. Ответ и ошибки

**Успех:**

```json
{ "success": true, "message": "Решение применено", "error": null }
```

**Ошибки** (легаси-конверт `{success, message, error}`):

| HTTP | Код                     | Ситуация                                                                                                                                   |
| ---- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 401  | `UNAUTHORIZED`          | Токен панели отсутствует или невалиден                                                                                                     |
| 404  | `RESOURCE_NOT_FOUND`    | Чек с таким `id` в CRM не найден                                                                                                           |
| 422  | `VALIDATION_ERROR`      | Нет `decline_reason` при `rejected`; неизвестный статус; недопустимый переход; неизвестный `gtin`; правка состава в терминальном состоянии |
| 500  | `INTERNAL_SERVER_ERROR` | Внутренняя ошибка                                                                                                                          |

## 6. Пример

Запрос:

```json
{
  "moderation_status": "rejected",
  "decline_reason": "NO_PRODUCT",
  "comment": "В чеке нет акционных позиций",
  "products": [
    { "gtin": "4600494601234", "is_promo": false },
    { "gtin": "4600494609012", "is_promo": false }
  ]
}
```

Ответ: `200` + `{"success": true, "message": "", "error": null}`.

## 7. Передача решения на промо-инстанс

Применив решение, CRM-бэк отправляет его в `PATCH /api/v1/crm/receipts/{id}` (§2.14):

| Поле панели              | Поле инстанса                                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `moderation_status`      | `status`: `pending`→`CHECKING`, `approved`→`ACCEPTED`, `rejected`→`REFUSED`, `suspended`→`SUSPENDED`, `need_photo`→`NEED_PHOTO` |
| `decline_reason`         | `decline_reason`                                                                                                                |
| `products` (весь состав) | `items[]`: `{name, gtin, quantity, price, accepted = is_promo}` — состав заменяется целиком                                     |
| `retail_chain_id`        | `store_name` + `store_inn` (из справочника сетей CRM)                                                                           |
| —                        | `fns_status` не пересылается: отсутствие поля значит «не менять»                                                                |

Эффекты на инстансе: письмо участнику о принятии/отклонении ставит сам инстанс (повторный статус письма не порождает); недопустимый переход вернёт `422`, и CRM-бэк должен показать его панели как ошибку применения.
