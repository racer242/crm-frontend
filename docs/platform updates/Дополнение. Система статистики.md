
# ТЗ: Статистика

## 1. Концепция

Промо-инстанс хранит реестр статистических отчётов. Каждый отчёт — именованный SQL-запрос с метаданными полей результата.

Отчёты создаются и управляются через **CRM-next-админку**. Выполнение — по идентификатору отчёта, который выбирается из списка по человекочитаемому названию.

Форматы результата:

- `json` — постранично, как обычные списки;
- `xlsx` — файл целиком, без ограничения по строкам.

## 2. Модель данных: запись отчёта

| Поле | Тип | Описание |
|----|----|----|
| `id` | UUID | Идентификатор отчёта |
| `title` | string | Название — его читает человек при выборе из списка |
| `sql` | text | SQL-запрос |
| `fields` | array | Метаданные полей выдачи |
| `is_active` | bool | Доступен ли отчёт для выполнения |

### 2.1. Метаданные полей выдачи (`fields[]`)

| Поле | Тип | Обяз. | Описание |
|----|----|----|----|
| `name` | string | да | Имя колонки в результате (алиас в SQL) |
| `title` | string | да | Человекочитаемый заголовок (для xlsx и отображения) |
| `type` | string | нет | Тип для форматирования: `string`, `number`, `money`, `date`, `datetime`, `boolean` |

## 3. Макросы подстановки

Макросы в тексте SQL обозначаются `{{NAME}}` и подставляются инстансом при выполнении.

| Макрос | Значение |
|----|----|
| `{{now}}` | Текущая дата/время |

На первое время достаточно `{{now}}`. Набор макросов расширяется по мере необходимости.

**Подстановка значений (обновление 08.10.26).** Сервер подставляет значения
макросов в текст SQL **как есть** — кавычки вокруг значений не добавляются.
Поэтому:
- даты `startDate`/`endDate` фронтенд отправляет уже закавыченными
  (`'2026-10-08 00:00:00'`) — адаптеры `stats.execute.request.js` /
  `stats.export.request.js` оборачивают их в кавычки (`sqlString` из
  `_shared.js`);
- `{{now}}` в тексте отчёта пишется в кавычках: `'{{now}}'`;
- пары из поля «Подстановки» подставляются как введены — строковые значения
  указываются в кавычках (в значении или в самом SQL отчёта).

## 4. Безопасность

| Мера | Описание |
|----|----|
| Только чтение | Разрешены `SELECT` и `WITH`. Модифицирующие операторы запрещены |
| Белый список таблиц | Перечень таблиц, к которым разрешено обращаться (можно предусмотреть) |
| Таймаут | Если запрос завис, процесс принудительно завершается и возвращается ошибка |

Параметризация, лимиты по числу строк и аудит в этой версии не реализуются.

| 5.2 | `/api/v1/crm/stats/reports/{id}` | GET | Детали отчёта |
| 5.3 | `/api/v1/crm/stats/reports` | POST | Создать отчёт |
| 5.4 | `/api/v1/crm/stats/reports/{id}` | PATCH | Обновить отчёт |
| 5.5 | `/api/v1/crm/stats/reports/{id}` | DELETE | Удалить отчёт |

Существующий `GET /api/v1/crm/stats/report/execute` **удаляется**.

**Поля записи отчёта (обновление 07.10.26):** `category` — категория использования: `STATISTICS` (отчёты) / `VIEW` (запросы); `for_dashboard` — boolean, показ выгрузки на дашборде (параметр на будущее); `view_type` — тип вывода статистики на дашборде: `TABLE` / `PIE` / `LINE` / `COLUMN` (параметр на будущее). `GET`-список (5.1) принимает query-параметр `category` для фильтрации.

### 5.1. `GET /api/v1/crm/stats/reports` — список отчётов

**Запрос (query):** `page`, `limit`, `is_active` (фильтр), `search` (по названию), `category` (`VIEW`/`STATISTICS`).

**Ответ (**`data.items[]`):

| Поле | Тип | Описание |
|----|----|----|
| `id` | UUID | Идентификатор |
| `title` | string | Название |
| `is_active` | bool | Активен ли |

Плюс `pagination`. SQL в списке не отдаётся — только в деталях (5.2).

### 5.2. `GET /api/v1/crm/stats/reports/{id}` — детали отчёта

**Ответ (**`data`): все поля записи, включая `sql` и `fields`.

### 5.3. `POST /api/v1/crm/stats/reports` — создать отчёт

**Запрос (body):** `title`, `sql`, `fields`, `is_active`, `category` (`STATISTICS` для отчётов, `VIEW` для запросов).

**Валидация:** проверка SQL по правилам §4; соответствие имён в `fields` алиасам результата (по возможности).

### 5.4. `PATCH /api/v1/crm/stats/reports/{id}` — обновить отчёт

Частичное обновление. Та же валидация, что при создании. Дополнительно принимаются `for_dashboard` (boolean) и `view_type` (`TABLE`/`PIE`/`LINE`/`COLUMN`) — при отсутствии поля значение не меняется.

### 5.5. `DELETE /api/v1/crm/stats/reports/{id}` — удалить отчёт

**Ответ (**`data`): признак удаления.

### 5.6. `POST /api/v1/crm/stats/reports/{id}/execute` — выполнить отчёт

**Запрос:**

| Параметр | Где | Тип | Обяз. | Описание |
|----|----|----|----|----|
| `id` | path | UUID | да | Идентификатор отчёта |
| `format` | body | string | нет | `json` (по умолчанию) или `xlsx` |
| `page` | query | int | нет | Страница (для `json`), по умолчанию 1 |
| `limit` | query | int | нет | Размер страницы (для `json`), по умолчанию 20, максимум 100 |
| `replacements` | body | object | нет | Подстановки макросов `{{NAME}}`: `startDate`/`endDate` (настенное время пояса сервера в одинарных кавычках, `'YYYY-MM-DD HH:mm:ss'`) и произвольные пары «имя → значение» из поля «Подстановки» (JSON) страницы запроса |

**`replacements` (обновление 07.10.26):** каждый ключ объекта становится доступным макросом `{{NAME}}` в SQL. Даты задаёт фронтенд (календари «Начало»/«Конец»), произвольные подстановки — JSON-поле «Подстановки» на странице запроса (`{"NAME": "Значение"}`); при конфликте ключей приоритетно значение из JSON. Значения подставляются в текст SQL как есть — сервер кавычки не добавляет: даты фронтенд присылает уже закавыченными, `{{now}}` и строковые значения из «Подстановок» пишутся в кавычках (§3, §9).

**Поведение:**

1. Проверка, что отчёт существует и `is_active = true`.
2. Подстановка макросов (`{{now}}` — в SQL отчёта в кавычках `'{{now}}'`; значения `replacements` вставляются текстом как есть, §3).
3. Выполнение SQL с таймаутом.
4. Для `json` — применение пагинации, возврат постранично.
5. Для `xlsx` — формирование файла со всеми строками.

## 6. Форматы ответа

### 6.1. `format=json`

Ответ строится по тому же принципу, что и списочные эндпоинты:

| Поле | Тип | Описание |
|----|----|----|
| `items` | array | Строки результата |
| `pagination` | object | `{page, limit, total_items, total_pages}` |

### 6.2. `format=xlsx`

Бинарный файл без обёртки `status`/`data`:

| Заголовок | Значение |
|----|----|
| `Content-Type` | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| `Content-Disposition` | `attachment; filename="{id}_{дата}.xlsx"` |

Заголовки колонок — из `fields[].title`. Ограничения по числу строк нет.

## 7. Механика выполнения

1. Проверка подписи и версии обмена (на префиксе).
2. Поиск отчёта по `id`; проверка `is_active`.
3. Проверка SQL по правилам §4.
4. Подстановка макросов.
5. Выполнение с таймаутом: зависший процесс убивается, возвращается ошибка.
6. Для `json` — пагинация результата; для `xlsx` — все строки.

Пагинация произвольного SQL применяется обёрткой: запрос выполняется как подзапрос, к нему применяются `LIMIT`/`OFFSET` и отдельный подсчёт общего числа строк.

## 9. Расхождения и решения

| Что в ТЗ | Как сделано | Почему |
| --- | --- | --- |
| «Белый список таблиц (можно предусмотреть)» | Не делаем; вместо него — запрет служебных схем (`mysql`, `information_schema`, `performance_schema`, `sys`) | Разбор имён таблиц в произвольном SQL ненадёжен, а отчёт по своим таблицам — штатная работа. Список пришлось бы править при каждой новой таблице |
| Подстановка `{{now}}` в текст запроса | Значение вставляется в текст SQL как есть; кавычки — на стороне, формирующей значение: даты `startDate`/`endDate` фронт присылает закавыченными, `{{now}}` в SQL отчёта пишется как `'{{now}}'` (обновление 08.10.26 — сервер перестал заключать значения макросов в кавычки) | Макрос без кавычек ломает SQL (`2026-10-08 00:00:00` — невалидный литерал); за кавычки отвечает тот, кто знает тип значения — фронт (даты) или текст отчёта (`{{now}}`, строки из «Подстановок») |
| Проверка `fields` «по возможности» | Проверяется всегда: пробный запуск с `LIMIT 0` даёт имена колонок | Опечатка в алиасе иначе всплыла бы пустым столбцом в выгрузке через неделю |
| Таймаут «процесс принудительно завершается» | Подсказка MySQL `MAX_EXECUTION_TIME(30000)` | Сервер обрывает запрос сам; PHP в этот момент ждёт ответа и убить ничего не может |
| Семь прежних отчётов (`report_type`) | Удалены без переноса (решение от 14.09.2026) | Реестр заводится заново из админки; два источника одних и тех же чисел разошлись бы |

**Чего решили не делать: отдельного пользователя базы только на чтение**
(решение от 14.09.2026). Это значит, что `ReportSqlGuard` — единственный заслон
между текстом отчёта и правами приложения. Практические следствия:

- проверка идёт и при сохранении, и **перед каждым выполнением**: запись в таблице
  могли поправить мимо API;
- исполняемые комментарии MySQL (`/*!32302 ; DROP TABLE … */`) разбираются как код,
  а не как комментарий — иначе через них прошёл бы второй оператор;
- `INTO OUTFILE`/`DUMPFILE` и `LOAD_FILE` запрещены словами: с правами на запись
  они позволили бы положить файл в каталог сайта;
- если когда-нибудь заведём пользователя с грантом только `SELECT`, всё это
  останется как первая линия, но перестанет быть единственной.

**Сортировка** задаётся внутри самого отчёта. Пагинация оборачивает запрос
в производную таблицу (`SELECT * FROM (…) LIMIT … OFFSET …`), а `ORDER BY`
в производной таблице MySQL сохраняет, но формально это не обещано — если порядок
важен, он должен быть в тексте отчёта.

**Персональные данные.** Отчёт видит всю базу, включая `user_extended` (паспорт,
ИНН, СНИЛС). Ограничений на состав колонок нет: это осознанная цена гибкости,
и доступ к реестру = доступ к выгрузке любых данных участников.

### 10.1. Запрос

`POST /api/v1/crm/stats/reports/{id}/execute`, формат `json`. Роут фронтенда
`ops/users-v2/report/[report_id]/execute` помечен `query: true` — весь вывод
request-адаптера уходит в query-строку (как у существующего execute; вложенный
`replacements` сервер принимает и из query — «JSON-объектом», §4.6 «Подробное
описание эндпоинтов CRM API»). Контракт execute — **только** `page`, `limit`
и `replacements`; отдельных `sort`/`direction`/`search`/`filters` в нём нет.

Макросы SQL отчёта — **фрагменты**: каждый `{{…_FILTER}}` — целое SQL-условие
(`AND u.status IN (…)`), `{{ORDER_BY}}`/`{{ORDER_DIR}}` — алиас колонки и
`ASC`/`DESC`. Значения подставляются в текст SQL, и сервер валидирует, что
каждому макросу отчёта передано значение: макрос без ключа в `replacements`
даёт `422` («Не переданы значения макросов»). Поэтому фрагменты собирает
request-адаптер (`stats.users.execute.request.js`) — отдельной серверной
«конфигурации маппинга» из спеки `.prompts/new_req_users.md` не существует, —
и все 9 ключей присутствуют в запросе всегда; неиспользуемый фильтр — пустая
строка.

```json
{
  "page": 3,
  "limit": 10,
  "replacements": {
    "STATUS_FILTER": "AND u.status IN ('active', 'blocked')",
    "PARTICIPANT_STATUS_FILTER": "",
    "MAILING_FILTER": "",
    "DATE_FROM_FILTER": "AND u.created_at >= '2026-09-01 03:00:00'",
    "DATE_TO_FILTER": "AND u.created_at <= '2026-10-01 02:59:59'",
    "BALANCE_FILTER": "AND u.balance BETWEEN 0 AND 10000",
    "SEARCH_FILTER": "AND (u.email LIKE '%иван%' OR u.participant_code LIKE '%иван%' OR u.first_name LIKE '%иван%' OR u.last_name LIKE '%иван%' OR u.phone LIKE '%иван%')",
    "ORDER_BY": "created_at",
    "ORDER_DIR": "DESC"
  }
}
```

- `page` = `Math.floor(first / limit) + 1`, `limit` = rows таблицы (SQL без
  LIMIT/OFFSET — сервер пагинирует и считает total сам, §9; максимум 100);
- **все 9 ключей макросов передаются всегда** — макрос без переданного
  значения даёт `422`; неиспользуемый фильтр — пустая строка;
- `STATUS_FILTER` / `PARTICIPANT_STATUS_FILTER` — `options`-фильтры: массив
  булевых по позициям opts → значения БД (`active`/`blocked`/`deleted`;
  `ANKET_REQUIRED`/`PARTICIPANT`) → `AND u.status IN ('active', 'deleted')`;
- `MAILING_FILTER` — радио «Согласие на рассылку»: метка опции (`Принял` /
  `Не принял` / `Все`; ничего не выбрано = «Все») → `AND u.mailing = 1` /
  `= 0` / `` (пустая строка — ограничений нет);
- `DATE_FROM_FILTER` / `DATE_TO_FILTER` — границы периода регистрации
  (мгновения `registration_date`) в настенном времени пояса сервера API
  (`toZonedDateTime` + `BITRIX_API_TIMEZONE`, как startDate/endDate) →
  `AND u.created_at >= '…'` / `<= '…'` — прямое сравнение в поясе хранения,
  без `CONVERT_TZ` (причина отказа — CHANGELOG от 07.10);
- `BALANCE_FILTER` — границы диапазона (валидуются как числа): `BETWEEN` при
  двух границах, `>=`/`<=` при одной;
- `SEARCH_FILTER` — `AND (u.email LIKE '%иван%' OR …)` по email, коду, имени,
  фамилии и телефону; `%`, `_`, `\` во вводе экранируются, апострофы
  удваиваются (фрагмент подставляется в SQL текстом — экранирование на фронте);
- `ORDER_BY` / `ORDER_DIR` — алиас из белого списка (`user_id`,
  `participant_code`, `email`, `status`, `participant_status`, `balance`,
  `total_earned`, `mailing`, `created_at`; `full_name` — выражение, не
  сортируется) и `ASC`/`DESC` (`sortOrder` −1 → `DESC`); без сортировки —
  дефолт `created_at` + `DESC`.

SQL отчёта (правится в админке; фрагментные макросы — правки SQL не требуют):

```sql
SELECT
    BIN_TO_UUID(u.id)                                AS user_id,
    u.participant_code,
    u.email,
    TRIM(CONCAT_WS(' ', u.first_name, u.last_name))  AS full_name,
    u.phone,
    u.status,
    u.participant_status,
    u.balance,
    u.total_earned,
    u.mailing,
    u.created_at
FROM `user` u
WHERE 1=1
  {{STATUS_FILTER}}
  {{PARTICIPANT_STATUS_FILTER}}
  {{MAILING_FILTER}}
  {{DATE_FROM_FILTER}}
  {{DATE_TO_FILTER}}
  {{BALANCE_FILTER}}
  {{SEARCH_FILTER}}
ORDER BY {{ORDER_BY}} {{ORDER_DIR}}
```

Значения макросов должны совпадать с реальными значениями БД: `u.status` —
`active`/`blocked`/`deleted`, `u.participant_status` —
`ANKET_REQUIRED`/`PARTICIPANT` (§2 спеки; если в базе иначе — правится
`STATUS_VALUES`/`PARTICIPANT_STATUS_VALUES` в адаптере).

### 10.2. Ответ

Response-адаптер (`stats.users.execute.response.js`) поддерживает оба формата:

- текущий (§6.1): `{items, pagination}` → `{value, totalRecords, first, rows}`;
- будущий (спека new_req_users §3): `{rows: [{id, values}], filters, search, meta}`
  → `value` из `rows[].values` (контракт «columns[].id = ключ в values»),
  счётчики — из `meta.total_count/first/limit`.

Колонки таблица берёт не из ответа execute, а из `state.report.columns` —
результата GET `ops/users-v2/report/[report_id]` (`stats.users.report.response.js`):
`{id, title, columns (из fields[]: field/header/sortable/dataType), filters}`.
SQL отчёта и служебные поля (`category`, `for_dashboard`, `view_type`…) наружу
не отдаются — фронтенд получает только имена, заголовки и типы колонок.

Адаптер execute пост-обрабатывает значения строк — подстановки для отображения
(сортировка и поиск уходят на сервер исходными кодами, SQL работает с ними):

- `status`/`participant_status` — коды БД (`active`/`blocked`/`deleted`,
  `ANKET_REQUIRED`/`PARTICIPANT`) заменяются читаемыми подписями — теми же
  словами, что в opts соответствующих фильтров (§10.3); неизвестный код
  проходит как есть;
- `mailing` (1/0) — вместо сырого значения строка получает поля
  `mailing_icon`/`mailing_severity` (зелёная галочка `pi pi-check-circle`/
  `success`, красный крестик `pi pi-times-circle`/`danger`, пусто при null —
  паттерн `is_promo` из карточек чеков); колонка «Рассылка» рисуется
  customColumn-кнопкой-иконкой с `visibleRow` — ячейка без данных пустая,
  сортируемость колонки сохраняется.

### 10.3. Фильтры страницы

Определения фильтров (§2 спеки: `status`, `participant_status`, `mailing`,
`registration_date`, `balance`) захардкожены в report-response-адаптере — с
лейблами (`name`), которые рисуют FiltersPanel и ActiveFiltersBar, — и приходят
странице в поле `filters` → живут в `state.report.filters`. Состав:

- `status` — «Статус участника», `options`: множественный выбор (Активен /
  Заблокирован / Удалён);
- `participant_status` — «Статус анкеты», `options`: множественный выбор
  (Анкета не заполнена / Участник);
- `mailing` — «Согласие на рассылку», `radio`: Принял / Не принял / Все;
  ничего не выбрано = «Все» (ограничений нет);
- `registration_date` — «Дата регистрации», `period` (два календаря);
- `balance` — «Баланс баллов», `range` **без `opts`**: без бегунка и без
  границ — свободные поля «От»/«До» (аналогия с периодом: не указано ни одно
  значение — вывод без ограничений).

Значения, выбранные пользователем, пишутся в тот же массив; ответ execute
фильтров не возвращает — форма не сбрасывается при пагинации. Когда сервер
начнёт эхо-возвращать `filters` (§3.4 спеки), адаптер отдаст серверные
определения вместо хардкода — конфиг страницы менять не придётся.

### 10.4. Параметры запроса: `state.usersQuery` (сортировка, поиск)

Ответ execute записывается в `state.users` **заменой** поля целиком
(`StateManager.setStateField`), а адаптер ответа возвращает только `value`,
`totalRecords`, `first`, `rows` — всё, что сервер не эхо-возвращает, при
каждом обновлении списка затиралось (сортировка работала — значения брались
из события `onSort` в request-адаптере, но индикатор в заголовке колонки не
отображался; строка поиска очищалась). Поэтому параметры запроса вынесены в
отдельный объект state страницы — `state.usersQuery` (по образцу фильтров,
живущих в `state.report.filters`):

- `sortField`/`sortOrder` — lazy-таблица управляется пропсами: `sortField`/
  `sortOrder` таблицы привязаны к `@state.usersQuery.*`, иначе PrimeReact не
  показывает индикатор сортировки и не переключает направление. Обработчик
  `onSort` перед `requestUsers` пишет `event.sortField`/`event.sortOrder` в
  `state.usersQuery` двумя командами `setProperty` с вложенным путём
  (`setStateField` поддерживает точечные пути); команда `mergeState` для
  этого не годится — она игнорирует поле пути и сливает в корень state
  страницы;
- `search` — строка поиска (`InputTextWithThrottle`) привязана к
  `@state.usersQuery.search` в обе стороны; `dataInit` восстанавливает её из
  URL (`?search=…`);
- `first`/`rows` остались в `state.users` — их адаптер возвращает в ответе
  (эхо), пагинатор показывает фактически применённые сервером значения.

`requestUsers` и `mergeUrlParams` читают `sortField`/`sortOrder`/`search` из
`state.usersQuery`, `first`/`rows` — из `state.users`, фильтры — из
`state.report.filters`. Синхронизация с URL не изменилась.

Ограничение: при перезагрузке страницы с URL `?sortField=email&sortOrder=-1`
данные запрашиваются отсортированными (SSR dataFeed читает `location.params`),
но индикатор в шапке не восстанавливается — `dataInit` пишет значение из URL
как строку, а пропсу `sortOrder` нужен числовой `1/-1` (в state остаётся
начальное `1`). Поиск из URL восстанавливается полностью.
