# ТЗ: Панель управления

## Часть 1. Обмен данными панели управления

Панель управления взаимодействует с двумя видами бэкендов. Протоколы обмена принципиально различаются.

---

## 1. Общая схема взаимодействия

| Компонент               | Протокол                                                                         | Назначение обмена                                                                                                      |
| ----------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Управляющий бэкенд      | Пользовательская авторизация через Битрикс, обмен токенами через `httpOnly`-куки | Управление кампаниями, контентом, справочниками, пулами кодов и призов, запуск розыгрышей, мониторинг проведения       |
| Бэкенды промо-инстансов | Подпись каждого запроса, версионирование обмена                                  | Управление данными участников, чеками, кодами, призами, баллами, розыгрышами, справочниками, ресурсами, очередью задач |

**Принцип разделения:** управляющий бэкенд работает с пользователем панели (администратором) как с субъектом; бэкенды инстансов работают с панелью как с доверенным сервисом группировки. Пользовательская сессия администратора не передаётся в промо-инстансы.

---

## 2. Обмен с управляющим бэкендом

### 2.1. Аутентификация

Система авторизации панели управления использует Битрикс как источник пользователей и выдачи сессионных токенов.

| Аспект                             | Значение                                                             |
| ---------------------------------- | -------------------------------------------------------------------- |
| Источник пользователей             | Битрикс                                                              |
| Валидация учётных данных           | Выполняется Битрикс                                                  |
| Выдача токенов                     | Выполняется Битрикс                                                  |
| Хранение токенов на стороне панели | `httpOnly`-куки                                                      |
| Доступ к токенам из кода браузера  | Отсутствует (`httpOnly`)                                             |
| Валидация токена на стороне панели | Локальная проверка подписи через общий секрет, без запроса к Битрикс |

### 2.2. Состав токенов

| Токен           | Назначение                                                    | Время жизни            |
| --------------- | ------------------------------------------------------------- | ---------------------- |
| `access_token`  | Подтверждение активной сессии, проверяется при каждом запросе | 900 секунд (15 минут)  |
| `refresh_token` | Получение новой пары токенов без повторного входа             | 604800 секунд (7 дней) |
| `user_data`     | Данные пользователя для отображения в интерфейсе              | 604800 секунд (7 дней) |

Все токены передаются в `httpOnly`-куки. Данные пользователя для интерфейса читаются на сервере панели при построении макета страницы, чтобы исключить мигание меню при загрузке.

### 2.3. Жизненный цикл сессии

#### Вход

| Шаг | Действие                                                                       |
| --- | ------------------------------------------------------------------------------ |
| 1   | Администратор вводит логин и пароль в форму входа                              |
| 2   | Браузер отправляет учётные данные на сервер панели                             |
| 3   | Сервер панели пересылает учётные данные в Битрикс для валидации                |
| 4   | Битрикс проверяет пользователя и возвращает пару токенов и данные пользователя |
| 5   | Сервер панели записывает токены в `httpOnly`-куки                              |
| 6   | Браузер получает данные пользователя и перенаправляется на рабочую страницу    |

#### Проверка сессии

| Шаг | Действие                                                                               |
| --- | -------------------------------------------------------------------------------------- |
| 1   | Браузер отправляет запрос на защищённую страницу (куки передаются автоматически)       |
| 2   | Сервер панели проверяет `access_token` локально через общий секрет                     |
| 3а  | Если токен валиден и срок действия достаточен — страница отображается                  |
| 3б  | Если токен валиден, но срок скоро истечёт — выполняется обновление                     |
| 3в  | Если токен истёк или недействителен — переход к обновлению или перенаправление на вход |

#### Обновление токенов

| Шаг | Действие                                                                |
| --- | ----------------------------------------------------------------------- |
| 1   | Сервер панели обнаруживает истёкший или скоро истекающий `access_token` |
| 2   | Сервер панели отправляет `refresh_token` в Битрикс                      |
| 3   | Битрикс возвращает новую пару токенов и обновлённые данные пользователя |
| 4   | Сервер панели обновляет `httpOnly`-куки                                 |
| 5   | Исходный запрос администратора повторяется с новыми токенами            |

Обновление выполняется сервером панели, а не кодом браузера. Браузер не вызывает обновление напрямую.

#### Завершение сессии

| Шаг | Действие                                                 |
| --- | -------------------------------------------------------- |
| 1   | Администратор нажимает кнопку выхода                     |
| 2   | Сервер панели читает `access_token` из куки              |
| 3   | Сервер панели отправляет токен в Битрикс для инвалидации |
| 4   | Сервер панели удаляет все куки                           |
| 5   | Браузер перенаправляется на страницу входа               |

Завершение сессии выполняется успешно даже если Битрикс недоступен: куки удаляются, ошибка инвалидации игнорируется.

### 2.4. Принципы безопасности обмена с управляющим бэкендом

| Принцип                            | Содержание                                                           |
| ---------------------------------- | -------------------------------------------------------------------- |
| Запросы к Битрикс только с сервера | Браузер никогда не обращается к Битрикс напрямую                     |
| Токены в `httpOnly`-куки           | Код браузера не имеет доступа к токенам                              |
| Локальная проверка подписи         | Сервер панели проверяет токен без запроса к Битрикс на каждый запрос |
| Общий секрет подписи               | Один и тот же секрет используется Битрикс и сервером панели          |

### 2.5. Конфигурация обмена с управляющим бэкендом

| Параметр                    | Назначение                                                   |
| --------------------------- | ------------------------------------------------------------ |
| Адрес Битрикс               | Базовый адрес для запросов к Битрикс                         |
| Внутренний секрет           | Секрет для внутренних запросов сервера панели к Битрикс      |
| Секрет подписи токенов      | Секрет для локальной проверки подписи токенов                |
| Имена куки                  | Имена куки для `access_token`, `refresh_token`, `user_data`  |
| Время жизни куки            | Время жизни каждого из трёх куки                             |
| Защищённые маршруты         | Список маршрутов, требующих сессии                           |
| Гостевые маршруты           | Список маршрутов, доступных без сессии                       |
| Максимум попыток обновления | Максимальное количество попыток обновления токенов за запрос |

## 3. Обмен с бэкендами промо-инстансов

### 3.1. Принцип обмена

Обмен односторонний: запросы идут только от панели управления к инстансу. Исходящих вызовов инстанс не делает. Пользовательской авторизации здесь нет, а в запросах ходят персональные данные участников, поэтому проверка складывается из трёх независимых слоёв.

| Слой                                       | Назначение                                   |
| ------------------------------------------ | -------------------------------------------- |
| Подпись запроса                            | Подтверждает авторство и целостность запроса |
| Окно времени с одноразовым идентификатором | Не даёт переиграть перехваченный запрос      |
| Список разрешённых адресов                 | Отсекает чужой источник                      |

Одного слоя недостаточно: подпись сама по себе не мешает отправить перехваченный запрос повторно, а без подписи одноразовый идентификатор можно «сжигать» чужому ключу.

### 3.2. Заголовки аутентификации

Все запросы к бэкендам инстансов несут обязательные заголовки подписи:

| Заголовок         | Значение                                                                                                             |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- |
| `X-Crm-Key-Id`    | Идентификатор ключа, выданного инстансом                                                                             |
| `X-Crm-Timestamp` | Время отправки, `unix`-секунды                                                                                       |
| `X-Crm-Nonce`     | Одноразовая строка запроса, формат: буквы, цифры, точка, подчёркивание, двоеточие, дефис; длина от 8 до 128 символов |
| `X-Crm-Signature` | Подпись запроса, шестнадцатеричная строка в нижнем регистре                                                          |

### 3.3. Канонический вид подписи

Подпись вычисляется как хеш с ключом от пяти строк, склеенных символом перевода строки:

| Строка | Содержание                                                                         |
| ------ | ---------------------------------------------------------------------------------- |
| 1      | Метод запроса в верхнем регистре                                                   |
| 2      | Цель запроса: путь и параметры запроса ровно так, как отправлены, без нормализации |
| 3      | Хеш тела запроса, шестнадцатеричная строка; для пустого тела — хеш пустой строки   |
| 4      | Метка времени (значение заголовка `X-Crm-Timestamp`)                               |
| 5      | Одноразовый идентификатор (значение заголовка `X-Crm-Nonce`)                       |

**Правила формирования канона:**

| Правило                                                          | Обоснование                                                                                                                        |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Подписывается цель запроса целиком, вместе с параметрами         | Иначе подменой параметров можно переписать фильтры и вытащить не тот срез данных                                                   |
| Цель передаётся как отправлена, без нормализации                 | Панель подписывает ту строку, которую кладёт в строку запроса; договариваться о порядке параметров и правилах кодирования не нужно |
| Хеш тела, а не само тело                                         | Канон остаётся коротким на порциях в мегабайты                                                                                     |
| Метка времени и одноразовый идентификатор внутри подписи         | Иначе их можно подменить, и защита от повтора обходится                                                                            |
| Сравнение подписей выполняется через функцию постоянного времени | Подбор подписи по времени ответа невозможен                                                                                        |

### 3.4. Версионирование обмена

Каждый запрос к инстансу несёт заголовок версии формата обмена `X-Exchange-Version: A.B.C`.

| Часть версии | Название                                                      | Когда меняется                                                         |
| ------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `A`          | Актуальная версия                                             | При структурных изменениях формата обмена                              |
| `B`          | Минимальная версия инстанса, способная обработать этот формат | Когда поддержка старых версий инстансов прекращается                   |
| `C`          | Итерация, не влияющая фатально                                | При внутренних уточнениях; в решении принять или отказать не участвует |

Инстанс с версией `V` принимает запрос, если выполняется условие: `B <= V <= A`.

| Условие       | Решение инстанса                 |
| ------------- | -------------------------------- |
| `B <= V <= A` | Обработать                       |
| `V < B`       | Отказать — инстанс устарел       |
| `V > A`       | Отказать — инстанс новее формата |

**Заголовок ответа инстанса:** каждый ответ под контуром управления несёт заголовок `X-Instance-Version` со значением версии инстанса. При расхождении версий панель видит, с каким инстансом она разговаривает, не заглядывая в его логи.

**Версия обмена не входит в подпись запроса.** Канон хеша с ключом менять не стали: риск подмены версии по дороге — только ложный отказ, сами данные по-прежнему защищены подписью.

### 3.5. Ключи доступа

Ключи доступа к инстансу — сущности на стороне инстанса, а не переменные окружения. Это обеспечивает ротацию без деплоя, выключение конкретного клиента и след обращений.

| Поле ключа                 | Назначение                                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| Идентификатор ключа        | Значение заголовка `X-Crm-Key-Id`; несколько ключей живут одновременно (ротация, разные среды) |
| Секрет подписи             | Секрет для вычисления подписи запросов                                                         |
| Список разрешённых адресов | Адреса или подсети; пусто — ограничения по адресу нет                                          |
| Признак активности         | Отзыв ключа мгновенный, выключенный ключ не находится                                          |
| След обращений             | Время последнего обращения, адрес, счётчик запросов — для разбора инцидентов                   |

Секрет хранится открытым и хеширован быть не может: по нему пересчитывается подпись входящего запроса.

**Правила эксплуатации:**

- Доступ к ключам только у администратора инстанса.
- Ротация — через новую запись или смену секрета; два активных ключа живут рядом, старый выключается после переключения панели на новый.
- На боевом сервере список разрешённых адресов обязателен.

### 3.6. Окно времени и защита от повтора

| Правило                             | Значение                                               |
| ----------------------------------- | ------------------------------------------------------ |
| Расхождение часов панели и инстанса | Не более 5 минут                                       |
| Одноразовый идентификатор           | Принимается один раз; повтор — ошибка повтора          |
| Порядок проверки                    | После подписи и до занятия одноразового идентификатора |

Порядок проверки выбран не случайно:

- **После подписи** — чтобы неаутентифицированный запрос не мог выяснить версию инстанса по коду ответа.
- **До занятия одноразового идентификатора** — отклонённый по версии запрос должен остаться повторяемым: панель правит заголовок версии и шлёт тот же запрос с тем же одноразовым идентификатором и меткой времени. Если бы идентификатор занимался раньше, отказ по версии превращал бы повтор в ошибку повтора.

### 3.7. Коды ошибок обмена с инстансами

| Код                       | Статус | Когда                                                                             |
| ------------------------- | ------ | --------------------------------------------------------------------------------- |
| `CRM_AUTH_REQUIRED`       | 401    | Не переданы заголовки подписи или недопустимый формат одноразового идентификатора |
| `CRM_KEY_UNKNOWN`         | 401    | Ключ не найден или отключён                                                       |
| `CRM_SIGNATURE_INVALID`   | 401    | Подпись не сошлась                                                                |
| `CRM_REQUEST_EXPIRED`     | 401    | Метка времени вне допустимого окна                                                |
| `CRM_REPLAY_DETECTED`     | 409    | Запрос с таким одноразовым идентификатором уже был обработан                      |
| `CRM_IP_NOT_ALLOWED`      | 403    | Адрес источника не разрешён для ключа                                             |
| `CRM_VERSION_REQUIRED`    | 400    | Отсутствует заголовок версии обмена                                               |
| `CRM_VERSION_INVALID`     | 400    | Заголовок версии некорректен                                                      |
| `CRM_VERSION_UNSUPPORTED` | 409    | Версия инстанса вне диапазона версии обмена                                       |

### 3.8. Ограничение частоты

| Параметр           | Значение                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------- |
| Лимит              | 600 запросов в минуту с адреса                                                           |
| Обоснование порога | Выкачивание выборки и заливка порций — легально частые запросы                           |
| Назначение лимита  | Не про бизнес-логику, а про то, чтобы неподписанный поток не доходил до базы за секретом |

### 3.9. Конфигурация обмена с инстансами

Для каждого инстанса панель должна быть сконфигурирована со следующими параметрами:

| Параметр               | Тип           | Назначение                                      |
| ---------------------- | ------------- | ----------------------------------------------- |
| Идентификатор инстанса | Идентификатор | Уникальный идентификатор инстанса               |
| Название               | Строка        | Человекочитаемое название для интерфейса панели |
| Идентификатор кампании | Идентификатор | Принадлежность инстанса к кампании              |
| Базовый адрес          | Адрес         | Базовый адрес инстанса, куда отправлять запросы |
| Идентификатор ключа    | Строка        | Значение заголовка `X-Crm-Key-Id`               |
| Секрет подписи         | Строка        | Секрет для вычисления подписи запросов          |

Список инстансов и ключей передаётся панели при настройке. Секреты не передаются по сети в открытом виде и хранятся безопасно.

| Ограничение частоты    | Отсутствует                          | 600 запросов в минуту с адреса           |
| Направление            | Панель ↔ Управляющий бэкенд          | Панель → Инстанс (одностороннее)         |

## 5. Принципы безопасности обмена

| Принцип                 | Содержание                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| Разделение протоколов   | Пользовательская сессия администратора не используется для запросов к инстансам            |
| Секреты не в браузере   | Токены управляющего бэкенда в `httpOnly`-куки; секреты подписи инстансов на сервере панели |
| Подпись каждого запроса | Данные персональные, целостность подтверждается подписью                                   |
| Защита от повтора       | Одноразовый идентификатор и окно времени                                                   |
| Ограничение по адресам  | На боевом сервере список обязателен                                                        |
| Ротация ключей          | Без деплоя, через новую запись или смену секрета                                           |
| След обращений          | Время, адрес, счётчик запросов — для разбора инцидентов                                    |
