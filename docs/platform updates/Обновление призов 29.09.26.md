## 1. Список призов — `GET /api/v1/crm/prizes` и `/api/v1/crm/users/[id]/prizes`

### 1.1. Фильтры

| Требование     | Статус         | Реализация                                                                                                            |
| -------------- | -------------- | --------------------------------------------------------------------------------------------------------------------- |
| `act_required` | ✅ Реализовано | `1`/`true` — только призы, требующие акта; `0`/`false` — только без акта. Неизвестное значение → `400 INVALID_SYNTAX` |

| `raffle_id`    | ✅ Реализовано | Только призы, выигранные в этом розыгрыше. Неизвестный розыгрыш → `404 RAFFLE_NOT_FOUND`                              |

**`search` ищет по:**

| Что ввели                                        | Как ищется                  |
| ------------------------------------------------ | --------------------------- |
| Идентификатор приза и владельца (UUID)           | Точное совпадение           |

| Почта и ФИО владельца                            | Вхождение подстроки         |
| Название и код позиции каталога                  | Вхождение подстроки         |
| Внешний идентификатор экземпляра (`external_id`) | Вхождение подстроки         |

Свободный экземпляр без владельца находится по названию, коду и `external_id`.

### 1.2. Вывод `act_required`

### 1.3. Сортировка по полям

❌ **Не реализовано в этом обновлении.** Параметр сортировки (`sort`, `order_by`) в §7.1 отсутствует. Это требует отдельной доработки.

### 1.4. Фильтр по розыгрышам

✅ Реализовано. Параметр `raffle_id` + поле `raffle_id` в ответе (розыгрыш, в котором приз выигран; `null` — выдан заказом, оператором или командой).

При отзыве приза (§7.6) и при возврате розыгрыша в черновик связь снимается вместе с владельцем.

## 3. Изменение статуса приза — `POST /api/v1/crm/prizes/[id]/status`

✅ Реализовано. Новый эндпоинт §7.8 (28.09.2026).

**Назначение:** решение оператора по выданному призу — то же, что кнопки «Подтвердить», «Отклонить», «Вернуть в ожидание» в админке инстанса. До этого из CRM статус приза менялся только через акт (§1.10), а у приза без акта — не менялся вовсе.

**Важно:** меняется статус выдачи (`status`), не состояние в пуле (`pool_status`) и не владелец: отзыв приза — §7.6, изъятие из пула — §7.7.

### Запрос

| Параметр | Где  | Тип    | Обяз. | Описание                                                               |
| -------- | ---- | ------ | ----- | ---------------------------------------------------------------------- |
| `id`     | path | UUID   | да    | Идентификатор приза (экземпляра)                                       |
| `status` | body | string | да    | `PENDING`, `ACT_UPLOADED`, `APPROVED`, `REJECTED` — без учёта регистра |

### Правила переходов

| Целевой статус | Условие                                                                                                                                             |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `APPROVED`     | У ценного приза (`act_required`) — только при загруженном подписанном акте: подтверждение означает «акт принят». Обычный приз подтверждается всегда |
| `REJECTED`     | Всегда. Приз остаётся за участником: отклонён документ, а не выдача                                                                                 |
| `ACT_UPLOADED` | Только при загруженном скане — иначе статус говорил бы неправду                                                                                     |
| `PENDING`      | Всегда; если скан загружен, приз переводится в `ACT_UPLOADED` (файл никуда не делся) — как кнопка «Вернуть в ожидание»                              |

Повтор того же статуса — не ошибка: CRM может отправить запрос заново.

### Ответ (`data`)

Карточка приза — те же поля, что элемент списка §7.1, плюс `updated_at` (ISO 8601, момент операции).

### Ошибки

| Ситуация                                           | Код                | HTTP |
| -------------------------------------------------- | ------------------ | ---- |
| `status` не передан                                | `INVALID_SYNTAX`   | 400  |
| Неизвестный статус                                 | `VALIDATION_ERROR` | 422  |
| Приз свободен (не выдан участнику) — менять нечему | `VALIDATION_ERROR` | 422  |
| `APPROVED` / `ACT_UPLOADED` без загруженного акта  | `VALIDATION_ERROR` | 422  |
| Приз не найден                                     | `PRIZE_NOT_FOUND`  | 404  |

## 4. Назначение и отзыв приза

### 4.1. `POST /api/v1/crm/users/[id]/prizes` — назначить приз (§7.5)

✅ Обновлено (28.09.2026).

**Ответ (`201 Created`):** карточка назначенного приза — те же поля, что элемент списка §7.1 (`prize_id`, `title`, `price`, `act_required`, `user_id`, `raffle_id`, `is_active`, `pool_status`, `status`). До 28.09.2026 отдавались только `prize_id` и `status` — они на месте, остальное добавлено.

**Новое правило:** повторное назначение того же приза тому же участнику — не ошибка: возвращается та же карточка, второго письма участнику не уходит.

✅ Обновлено (28.09.2026).

**Ответ (`data`):** карточка уже свободного экземпляра — те же поля, что элемент списка §7.1 (`user_id` и `raffle_id` уже `null`, `status` — `PENDING`), плюс:

| --------- | ---- | -------------- |

До 28.09.2026 отдавался только `revoked`.

**Принципы без изменений:** состояние в пуле отзыв не меняет; списанные баллы автоматически не возвращаются (§6.2).

## 5. Админка инстанса (дополнительно)

Из файла «12.ТЗ_Prizes_List.md» — раздел «Статус выдачи в админке (28.09.2026)»:

| Кнопка             | Статус                       | Условие показа                                 |
| ------------------ | ---------------------------- | ---------------------------------------------- |
| Подтвердить        | `APPROVED`                   | Экземпляр выдан участнику и ещё не подтверждён |
| Отклонить          | `REJECTED`                   | Экземпляр выдан участнику и ещё не отклонён    |
| Вернуть в ожидание | `PENDING` или `ACT_UPLOADED` | Экземпляр выдан участнику и статус изменится   |

**Ключевые решения:**

- `ACT_UPLOADED` кнопкой не ставится — этот статус означает, что файл акта лежит в хранилище, и ставит его загрузка документа
- «Вернуть в ожидание» смотрит на файл: если подписанный акт загружен, экземпляр возвращается в `ACT_UPLOADED`, а не в `PENDING`
- Подтвердить ценный приз без акта нельзя — то же правило, что в CRM (§1.10). Правило живёт в `PrizeInstance::canBeApproved()` — одно на админку и на CRM
- Свободному экземпляру пула кнопки не показываются
- Отклонение не отзывает приз — экземпляр остаётся за участником

Также добавлено поле `image` в список призов (23.09.2026) — локальный адрес картинки, тот же вид, что в витрине `GET /api/v1/prizes/available`.

## Дополнение (октябрь 2026): справочник статусов в ответах

API вместе с данными возвращает справочник статусов выдачи приза — в списках (`GET /api/v1/crm/prizes`, `GET /api/v1/crm/users/[id]/prizes`) и в карточке (`GET /api/v1/crm/prizes/{id}`) — поле `data.statuses`, массив `{value, name}` (на момент дополнения — 14 значений: `FREE`, `SENDING`, `SENT`, `ERROR`, `RECEIVED`, `DOWNLOAD`, `DATA_NEEDED`, `PROCESSING`, `READY_FOR_DELIVERY`, `NEED_CODE`, `DELETED`, `PENDING`, `ACT_UPLOADED`, `REJECTED`).

Панель использует справочник как источник опций фильтра «Статус...» обоих списков призов и дропдауна смены статуса на карточках (плашка «Управление» переименована в «Статус приза») — жёстко зашитые в конфигах страниц словари удалены, новые статусы подхватываются без правок фронтенда. Подпись «Статус» в списках при отсутствии `status_label` у элемента также берётся из справочника (фолбэк — прежний словарь четырёх статусов обновления 29.09.26, затем сырой код).
