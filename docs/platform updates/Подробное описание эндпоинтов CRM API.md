## 1. Модель доступа и аутентификация

Свод единый для всех доверенных бэкендов группировки. Обмен односторонний (инстанс → инстанс). Проверка складывается из трёх независимых слоёв: подпись подтверждает авторство и целостность, окно времени с одноразовым `nonce` не даёт переиграть перехваченный запрос, список адресов отсекает чужой источник.

### 1.1. Заголовки аутентификации (обязательны для всех эндпоинтов)

| Заголовок         | Значение                                                    |
| ----------------- | ----------------------------------------------------------- |
| `X-Crm-Key-Id`    | Идентификатор ключа, выданного инстансом                    |
| `X-Crm-Timestamp` | Время отправки, unix-секунды                                |
| `X-Crm-Nonce`     | Разовая строка запроса, `[A-Za-z0-9._:-]{8,128}`            |
| `X-Crm-Signature` | `hash_hmac('sha256', канон, секрет)`, hex в нижнем регистре |

### 1.2. Канонический вид подписи

Подписываются пять строк, склеенных `\n`:

```
МЕТОД                 (в верхнем регистре: GET, POST, PATCH, DELETE)
ЦЕЛЬ-ЗАПРОСА          (путь и query ровно так, как отправлены, без нормализации)
sha256(тело)          (hex; для пустого тела — sha256 пустой строки)
TIMESTAMP             (значение заголовка X-Crm-Timestamp)
NONCE                 (значение заголовка X-Crm-Nonce)
```

Подписывается цель запроса целиком вместе с query: иначе подменой параметров можно было бы переписать фильтры. Хэш тела вместо тела — чтобы канон оставался коротким на больших порциях.

Метод на обработку цели не влияет: `POST` со строкой запроса подписывается так же, как `GET`. Отличается только хэш тела.

### 1.3. Две частые причины `CRM_SIGNATURE_INVALID`

**Query дописан после подписи.** Клиент собирает канон из пути, а параметры передаёт через `params`/`query`, и библиотека добавляет их в адрес уже при отправке. Симптом: запросы без параметров проходят, с `?page=2` — нет. Лечится сборкой канона из итогового адреса либо передачей параметров в теле.

**Тело подписано не тем, что отправлено.** `JSON.stringify(undefined)` возвращает `undefined`, `fetch` отправляет пустое тело, а подпись посчитана от `"{}"`. Пустое тело и `{}` дают разные хэши:

| Тело  | sha256                                                             |
| ----- | ------------------------------------------------------------------ |
| пусто | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` |
| `{}`  | `44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a` |

При отказе по подписи в `error.details` возвращается то, из чего инстанс собрал канон:

```json
{"field": "method",         "issue": "POST"}
{"field": "request_target", "issue": "/api/v1/crm/stats/reports/…/execute?format=xlsx"}
{"field": "body_sha256",    "issue": "e3b0c442…52b855"}
{"field": "body_length",    "issue": "0"}
```

### 1.4. Команда диагностики

```
php bin/console app:crm:signature <key-id> <метод> '<request_target>' <timestamp> <nonce> <signature> \
    --body-hash=<body_sha256 из ответа> --host=<домен> --env=prod
```

Секрет команда не печатает — только называет сошедшийся вариант.

### 1.5. Правила проверки

- Расхождение часов инстанс ↔ клиент — не более 5 минут, иначе `CRM_REQUEST_EXPIRED`.
- `nonce` принимается один раз; повтор — `CRM_REPLAY_DETECTED`.
- Адрес источника сверяется со списком, настроенным на ключ; на проде список обязателен, иначе `CRM_IP_NOT_ALLOWED`. Проверку можно снять пустым списком у ключа или `CRM_IP_CHECK_ENABLED=0` в конфигурации сервера (добавлено 2026-09-11). Каждый пропущенный вне списка запрос пишется в лог.
- Ключи заводятся и ротируются командой `app:crm:client`.

### 1.6. Коды ошибок доступа

| HTTP | Код                     | Когда                                    |
| ---- | ----------------------- | ---------------------------------------- |
| 401  | `CRM_AUTH_REQUIRED`     | Не переданы заголовки подписи            |
| 401  | `CRM_KEY_UNKNOWN`       | Ключ неизвестен или отключён             |
| 401  | `CRM_SIGNATURE_INVALID` | Подпись не сошлась                       |
| 401  | `CRM_REQUEST_EXPIRED`   | Метка времени вне допустимого окна       |
| 409  | `CRM_REPLAY_DETECTED`   | Запрос с таким `nonce` уже был обработан |
| 403  | `CRM_IP_NOT_ALLOWED`    | Адрес источника не разрешён для ключа    |

## 1.1. `GET /api/v1/crm/users` — список участников

**Назначение:** пагинированный список участников для просмотра и управления. Поддерживает фильтрацию и поиск.

**Код участника (с 2026-09-11):** в каждой записи едет `participant_code` вида `54XVKDQ8` — короткий идентификатор, который участник видит в кабинете и называет поддержке. Параметр `search` ищет и по нему: код сравнивается целиком без учёта регистра, почта и ФИО — подстрокой. У участников до выкладки код появляется после команды `app:user:participant-codes`.

**Запрос:**

| Параметр        | Где   | Тип    | Обяз. | Описание                                                               |
| --------------- | ----- | ------ | ----- | ---------------------------------------------------------------------- |
| `page`, `limit` | query | int    | нет   | Пагинация                                                              |
| `status`        | query | string | нет   | Фильтр по статусу участника                                            |
| `email`         | query | string | нет   | Поиск по почте                                                         |
| `search`        | query | string | нет   | Поиск одной строкой: код участника, идентификатор, почта, ФИО, телефон |

**Правила `search` (расширено 22.09.2026):**

| Что ввели                     | Как ищется                                                                              |
| ----------------------------- | --------------------------------------------------------------------------------------- |
| Код участника (`54XVKDQ8`)    | точное совпадение, регистр не важен                                                     |
| Идентификатор (UUID)          | точное совпадение; колонка `BINARY(16)` — отдельная ветка                               |
| Почта, имя, фамилия, отчество | вхождение подстроки                                                                     |
| Телефон                       | по цифрам: номер хранится как ввёл участник, и `9161234567` найдёт `+7 (916) 123-45-67` |

**Пример запроса:**

```
GET /api/v1/crm/users?page=1&limit=20&search=Иванов
```

| `first_name`, `last_name`, `third_name` | string\|null | ФИО                           |
| `status`                                | string       | Статус                        |
| `created_at`                            | datetime     | Дата регистрации              |

## 1.2. `GET /api/v1/crm/users/[id]` — участник подробно (полная карточка)

**Назначение:** возвращает исчерпывающие данные участника в одном ответе — базовый профиль, расширенную анкету (паспорт, ИНН, СНИЛС), факт согласия, загруженные документы. Это единственное место в CRM API, откуда отдаются экстра-данные участника.

**Запрос:**

| Параметр | Где  | Тип  | Обяз. | Описание                |
| -------- | ---- | ---- | ----- | ----------------------- |
| `id`     | path | UUID | да    | Идентификатор участника |

**Ответ (`data`) — базовые данные участника:**

| Поле                                    | Тип          | Описание                                                           |
| --------------------------------------- | ------------ | ------------------------------------------------------------------ |
| `id`                                    | UUID         | Идентификатор участника                                            |
| `email`                                 | string       | Почта                                                              |
| `status`                                | string       | Статус участника                                                   |
| `created_at`                            | datetime     | Дата регистрации                                                   |
| `first_name`, `last_name`, `third_name` | string\|null | ФИО (базовый профиль)                                              |
| `phone`                                 | string\|null | Телефон                                                            |
| `city_id`                               | string\|null | Ключ города в `dict_cities`; `null` — город задан только названием |
| `city`                                  | string\|null | Название города: из справочника либо как ввели                     |
| `mailing`                               | string       | Признак рассылки (`"1"` / `"0"`)                                   |
| `points`                                | int          | Текущий баланс баллов                                              |

**Ответ (`data`) — расширенная анкета (`extra`):**

| Поле                                    | Тип          | Описание                                       |
| --------------------------------------- | ------------ | ---------------------------------------------- |
| `extra.personal.first_name`             | string       | Имя (из расширенной анкеты)                    |
| `extra.personal.last_name`              | string       | Фамилия                                        |
| `extra.personal.third_name`             | string\|null | Отчество                                       |
| `extra.extended.inn`                    | string\|null | ИНН (12 цифр физлицо / 10 юрлицо)              |
| `extra.extended.snils`                  | string\|null | СНИЛС (11 цифр)                                |
| `extra.extended.passport_series_number` | string\|null | Серия и номер паспорта (10 цифр)               |
| `extra.extended.passport_issue_date`    | string\|null | Дата выдачи паспорта                           |
| `extra.extended.passport_issued_by`     | string\|null | Кем выдан паспорт                              |
| `extra.extended.passport_address`       | string\|null | Адрес регистрации                              |
| `extra.agreement`                       | bool         | Факт согласия на обработку персональных данных |
| `extra.documents`                       | object       | Загруженные документы по типам                 |

**Документы (`extra.documents`)** — объект, ключ = тип документа, значение = `{ "file_id": string, "url": string }`.

| Ключ            | Описание                       |
| --------------- | ------------------------------ |
| `passport_main` | Паспорт (первая страница)      |
| `passport_reg`  | Паспорт (разворот регистрации) |
| `inn_scan`      | Свидетельство ИНН              |
| `snils_scan`    | Свидетельство СНИЛС            |

**База адресов файлов:** `url` отдаётся без базового адреса (решение от 2026-09-07). База у контура — `/api/v1/crm`, а не `/api/v1` (уточнено 21.09.2026). Все адреса файлов отдаются относительно неё и `/crm` в начале не содержат. Исправлено 19.09.2026: раньше стоял участниковский адрес `/users/profile/extra/document/{id}`, которому нужен JWT владельца — CRM получала `404`. Теперь отдаётся `/users/{userId}/document/{documentId}` (§1.2.1).

**Примечания:**

- Два набора ФИО независимы и могут отличаться — оба присутствуют в ответе.
- При отсутствии расширенной анкеты `extra` возвращается с пустыми структурами: `personal` и `extended` — пустые значения, `agreement` — `false`, `documents` — пустой объект. Поле `extra` не отсутствует и не `null`.

## 1.2.1. `GET /api/v1/crm/users/[userId]/document/[documentId]` — скан документа (файл)

**Назначение:** файл документа расширенной анкеты для модератора. Токена участника у инстанса нет, поэтому доступ закрывает подпись запроса.

**Запрос:**

| Параметр     | Где  | Тип  | Обяз. | Описание                                           |
| ------------ | ---- | ---- | ----- | -------------------------------------------------- |
| `userId`     | path | UUID | да    | Участник — владелец документа                      |
| `documentId` | path | UUID | да    | Идентификатор файла из `extra.documents[].file_id` |

**Ответ:** сам файл (`Content-Type` из записи, `Content-Disposition: inline`, `Cache-Control: private, no-store` — персональные данные). Конверта `status`/`data` нет.

Участник в адресе обязателен, хотя идентификатор документа уникален сам по себе: так запрос нельзя выполнить, зная лишь идентификатор скана, а ошибка в карточке даёт `404`, а не показ постороннего паспорта.

**Коды ошибок:**

| Ситуация                                                     | Код                      |
| ------------------------------------------------------------ | ------------------------ |
| Участника нет                                                | `404 USER_NOT_FOUND`     |
| Документа нет, принадлежит другому участнику или файл пропал | `404 RESOURCE_NOT_FOUND` |

| `users`                                         | body | array  | да    | Массив объектов участников |
| `users[].email`                                 | body | string | да    | Почта                      |
| `users[].first_name`, `last_name`, `third_name` | body | string | нет   | ФИО                        |

**Пример запроса:**

```json
{
  "users": [
    {
      "email": "petrov@example.com",
      "first_name": "Пётр",
      "last_name": "Петров"
    }
  ]

```

**Ответ (`data`):**

| Поле        | Тип   | Описание                          |
| ----------- | ----- | --------------------------------- |
| `imported`  | int   | Успешно импортировано             |
| `skipped`   | int   | Пропущено (дубликаты/ошибки)      |
| `results[]` | array | Статус по каждой ошибочной записи |

## 1.4. `PATCH /api/v1/crm/users/[id]` — изменить данные участника

**Назначение:** частичное обновление анкетных данных участника администратором.

**Запрос:**

| Параметр                                                  | Где  | Тип    | Обяз. | Описание                      |
| --------------------------------------------------------- | ---- | ------ | ----- | ----------------------------- |
| `id`                                                      | path | UUID   | да    | Идентификатор                 |
| `first_name`, `last_name`, `third_name`, `phone`, `email` | body | string | нет   | Обновляемые поля              |
| `city_id`                                                 | body | string | нет   | Ключ города из `dict_cities`  |
| `city`                                                    | body | string | нет   | Название города (ручной ввод) |
| `status`                                                  | body | string | нет   | Новый статус                  |

**Город в двух видах (уточнено 2026-09-08):**

- `city_id` — ключ записи `dict_cities`. Неизвестный или погашенный ключ → `422 VALIDATION_ERROR` с полем `city_id`. Основной путь.
- `city` — название. Опознаётся в справочнике по названию; однозначное совпадение сохраняется ссылкой, иначе остаётся текстом. Одноимённые города в разных регионах не разгадываются.
- Пришли оба — главнее `city_id`. Пустая строка убирает город.

**Ответ (`data`):** обновлённые поля участника, включая `city_id` и `city`.

## 2.14. `PATCH /api/v1/crm/receipts/[id]` — изменить чек

**Назначение:** результат работы инстанса-клиента над чеком — решение модератора и результат проверки в ФНС вместе с составом чека.

Письмо участнику отправляет инстанс (с 2026-09-11): при переводе в `ACCEPTED` или `REFUSED` в очередь ставится письмо о решении. У клиента контактов участника нет. Повторный `PATCH` с тем же статусом письма не порождает.

**Запрос:**

| Параметр                            | Где  | Тип    | Обяз. | Описание                                                          |
| ----------------------------------- | ---- | ------ | ----- | ----------------------------------------------------------------- |
| `id`                                | path | UUID   | да    | Идентификатор чека                                                |
| `status`                            | body | string | да    | Статус чека; при отсутствии → `400 INVALID_SYNTAX`                |
| `decline_reason`                    | body | string | нет   | Причина отклонения                                                |
| `fns_status`                        | body | string | нет   | Результат проверки в ФНС (`no_check`, `wait`, `wrong`, `correct`) |
| `items[]`                           | body | array  | нет   | Состав чека: `{name, gtin?, quantity?, price?, accepted?}`        |
| `store_inn`, `store_name`, `region` | body | string | нет   | Данные магазина                                                   |
| `date`                              | body | string | нет   | Исправленное время покупки (добавлено 17.09.2026)                 |

**Пример запроса:**

```json
{
  "status": "ACCEPTED",
  "fns_status": "correct",
  "items": [
    {
      "name": "Напиток Schweppes 0,9л",
      "gtin": "4600494712345",
      "quantity": 2,
      "price": 8990,
      "accepted": true
    }
  ],
  "store_inn": "7707083893",
  "store_name": "Магнит у дома",
  "region": "77"
}
```

**Ответ (`data`):** `receipt_id`, `status`, `fns_status`, `updated_at`.

**Правила применения:**

- Отсутствие поля значит «не менять», а не «обнулить».
- `status` тот же, что уже стоит, — не ошибка. Сразу после проверки в ФНС клиент присылает `PATCH` с тем же `CHECKING`, только чтобы доехали `fns_status` и состав. Через машину состояний такой запрос не идёт, поэтому модератор и `moderated_at` не меняются. Недопустимый переход (например, `ACCEPTED` → `NEED_PHOTO`) → `422 VALIDATION_ERROR` с полем `status`.
- `items` заменяют состав целиком. `quantity` по умолчанию `1`, `price` — в копейках, `accepted` — `false`. Битая позиция отклоняет весь запрос (`422`, поле `items`).

**Длины полей проверяются на входе (23.09.2026):**

| Поле           | Предел                    |
| -------------- | ------------------------- |
| `items[].gtin` | 20 символов               |
| `items[].name` | 500 символов (обрезается) |
| `store_inn`    | 20                        |
| `store_name`   | 500                       |
| `region`       | 100                       |

`gtin` — это код товара, а не код маркировки. Из марки нужно взять именно GTIN.

Флаг `accepted` берётся как есть и по справочнику `dict_products` не пересчитывается.

**Причина отказа:** значение из перечисления инстанса (`DUPLICATE`, `WRONG_CHECK`, `NO_PRODUCT`, `BAD_PHOTO`, `OTHER`) применяется как есть, любой другой текст ложится в `OTHER` + комментарий модератора.

**`date` чинит время покупки (17.09.2026).** Значение читается по тем же правилам, что при регистрации: берётся то время, что в строке, метка пояса только помечает пояс и ничего не сдвигает. `2026-09-16T08:17:20+05:00` → в ФНС уйдёт `t=20260916T0817`. Нераспознанная строка → `400 WRONG_DATE`. Окно акции здесь не проверяется. Вместе с датой пересчитывается хэш дедупликации и обновляется `date_raw`.

**Ответ (`data`):** `{"deleted": true, "id": "…"}`.

## 4.6. `POST /api/v1/crm/stats/reports/[id]/execute` — выполнить отчёт

**Запрос:**

| Параметр       | Где            | Тип    | Обяз. | Описание                                                                                             |
| -------------- | -------------- | ------ | ----- | ---------------------------------------------------------------------------------------------------- |
| `id`           | path           | UUID   | да    | Идентификатор отчёта                                                                                 |
| `format`       | body           | string | нет   | `json` (по умолчанию) или `xlsx`                                                                     |
| `replacements` | body или query | object | нет   | Значения макросов запроса. В строке запроса — JSON-объектом или россыпью `replacements[startDate]=…` |
| `page`         | query          | int    | нет   | Страница для `json`                                                                                  |
| `limit`        | query          | int    | нет   | Размер страницы для `json` (по умолчанию 20, максимум 100)                                           |

`format=xlsx` принимается и в строке запроса — так ссылку на выгрузку можно открыть прямо в браузере.

**Макросы запроса.** В тексте отчёта могут стоять макросы `{{имя}}` с произвольными именами; их значения приходят в `replacements` и подставляются связанными параметрами, а не текстом. Встроен только `{{now}}` — время считает сервер. Макрос, для которого значение не передали, даёт `422` с перечислением недостающих имён: пустая подстановка вернула бы пустой отчёт, неотличимый от «данных нет».

**Пример запроса:**

```
POST /api/v1/crm/stats/reports/019faab9-1a2b-7c3d-8e4f-5a6b7c8d9e0f/execute
```

```json
{
  "format": "json",
  "replacements": { "startDate": "2026-09-01" }
}
```

**Ответ для `json` (`data`):** `items` (строки результата как их вернула база) и `pagination`.

**Ответ для `xlsx`:** файл без конверта `status`/`data`, `Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, имя `{id}_{дата}.xlsx`. Колонки и их порядок берутся из `fields`; строки не ограничены.

**Отказы:**

- Выключенный отчёт (`is_active = false`) — `422`, а не пустая выдача.
- Отчёт с незаполненным запросом — `422` «У отчёта не заполнен запрос».
- Запрос, нарушающий правила безопасности, — `422` (проверка идёт перед каждым выполнением: текст мог измениться в базе мимо API).
- Отчёт, не уложившийся в 30 секунд, прерывается сервером базы и отвечает `422` с явным сообщением.

## 7.2. `POST /api/v1/crm/prizes/import` — синхронизация пула призов

**Назначение:** синхронизация пула призов с входящим эталонным списком. Пул призов — все возможные призы, где каждая запись — один реальный приз. Логика синхронизации идентична кодам.

**Канал не канонический (с 2026-09-10).** Канонический канал — `POST /api/v1/crm/prizes/stock` (§7.7). Этот эндпоинт остаётся рабочим для внешних систем, у которых пул действительно поштучный. **Логика синхронизации:**

| Ситуация                                             | Действие                                                           | Счётчик   |
| ---------------------------------------------------- | ------------------------------------------------------------------ | --------- |
| Приз есть в импорте, отсутствует в пуле              | Добавляется в пул                                                  | `added`   |
| Приз есть в импорте и в пуле, атрибуты изменились    | Обновляется на месте                                               | `updated` |
| Приз есть в импорте и в пуле, атрибуты не изменились | Не изменяется, не учитывается                                      | —         |
| Приза нет в импорте, приз назначен участнику         | Помечается к изъятию: `pool_status = removing`, запись сохраняется | `updated` |
| Приза нет в импорте, приз не назначен                | Удаляется из пула                                                  | `removed` |

**Запрос:**

| Параметр | Где  | Тип   | Обяз. | Описание                                              |
| -------- | ---- | ----- | ----- | ----------------------------------------------------- |
| `prizes` | body | array | да    | Эталонный список призов (каждый — один реальный приз) |

**Ответ (`data`) — сводка синхронизации:**

| Поле      | Тип | Описание                                                      |
| --------- | --- | ------------------------------------------------------------- |
| `added`   | int | Добавлено новых призов                                        |
| `updated` | int | Изменено текущих записей (обновление атрибутов + деактивация) |
| `removed` | int | Удалено призов                                                |

## 7.7. `POST /api/v1/crm/prizes/stock` — план призов кампании

**Назначение:** клиент присылает план — какие позиции есть у акции и сколько экземпляров каждой должно существовать. Инстанс приводит к нему каталог и пул: заводит недостающие экземпляры, убирает лишние свободные, снимает позиции вне плана.

Ответственность разделена так: клиент владеет каталогом и планом (состав позиций, количество, стоимость, требование акта), инстанс владеет экземплярами (заводит по плану, выдаёт участникам, ведёт статусы и историю). Сколько призов выдано, знает только инстанс.

`stock` — это план, а не остаток. Выдачи из него не вычитаются: план — общее число экземпляров позиции, включая уже выданные.

**Запрос:**

| Параметр | Где  | Тип   | Обяз. | Описание                               |
| -------- | ---- | ----- | ----- | -------------------------------------- |
| `prizes` | body | array | да    | План кампании целиком, до 5000 позиций |

**Элемент списка — позиция каталога, не экземпляр:**

| Поле           | Тип            | Обяз. | Описание                                                    |
| -------------- | -------------- | ----- | ----------------------------------------------------------- |
| `code`         | string (≤100)  | да    | Ключ позиции в каталоге                                     |
| `type_code`    | string (≤100)  | нет   | Код типа приза (раздел каталога)                            |
| `title`        | string (≤255)  | да    | Название                                                    |
| `description`  | string         | нет   | Короткое описание                                           |
| `price`        | int ≥ 0        | нет   | Денежная стоимость, рубли                                   |
| `points_cost`  | int ≥ 0        | нет   | Цена заказа в баллах                                        |
| `act_required` | bool           | нет   | Нужен ли подписанный акт                                    |
| `image`        | string (≤1000) | нет   | Подписанная ссылка на картинку                              |
| `stock`        | int 0…100000   | да    | План: сколько экземпляров позиции всего должно существовать |
| `is_active`    | bool           | нет   | Позиция видна участникам; по умолчанию `true`               |

Числа и флаги принимаются и строкой (`"1500"`, `"Y"`, `"N"`). Непереданное поле и пустая строка неразличимы — значит «не прислали», текущее значение остаётся.

**Синонимы полей (приняты 2026-09-10):**

| Синоним    | Значение                                         |
| ---------- | ------------------------------------------------ |
| `count`    | то же, что `stock`; при обоих выигрывает `stock` |
| `cost_rub` | денежная стоимость в рублях                      |

Присланный `cost_rub` означает, что запрос написан по «Дополнению»: тогда рубли берутся из него, а `price` читается как баллы, если `points_cost` не передан. Без `cost_rub` действует форма клиента: `price` — рубли, баллы только в `points_cost`.

**Два флага позиции каталога:**

| Флаг         | Кто ставит | Что означает                                                                                                                                                      |
| ------------ | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `is_active`  | Клиент     | Видимость. Скрытая позиция не попадает в выборки участника, но её пул остаётся в нужном размере. Обратимо                                                         |
| `is_removed` | Инстанс    | Позиции нет в присланном плане. Запись каталога сохраняется для истории, свободные экземпляры уходят, выданные помечаются к изъятию. Вернулась в план — флаг снят |

Видимость приза участнику — это `is_active = true AND is_removed = false` и экземпляр в пуле; каскадного обновления экземпляров при смене флагов нет.

**Состояние экземпляра в пуле (`pool_status`):**

| Значение   | Смысл                                                                                           |
| ---------- | ----------------------------------------------------------------------------------------------- |
| `active`   | Экземпляр числится в пуле: свободен либо выдан участнику. Только такие считаются в размере пула |
| `removing` | Приз у владельца помечен к изъятию: связи целы, место в плане он больше не занимает             |
| `removed`  | Изъятие завершено. Только история — синхронизация такие записи не поднимает никогда             |

Переход `removing → removed` (после возврата баллов или замены приза) синхронизация не делает: механики награждения на инстансе нет, разбирает оператор — §7.6 отзывает приз, §6.2 правит баллы.

**Правило приведения к плану.** Для каждой присланной позиции: по `code` находится или создаётся позиция каталога, применяются атрибуты (в том числе план — он хранится в каталоге), затем число её экземпляров в пуле приводится к `stock`. Далее `A` — экземпляров в пуле, `F` — из них свободных.

| Ситуация                 | Действие (строго в этом порядке)                                                                                                          | Счётчики                                        |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `A < stock`              | Сначала возвращаются в пул экземпляры со статусом `removing` (сначала владельцы, среди них самые давние), затем создаются новые свободные | `instances.restored`, `created`                 |
| `A = stock`              | Ничего не меняется                                                                                                                        | `instances.kept`                                |
| `A > stock`, хватает `F` | Удаляются лишние свободные (самые свежие)                                                                                                 | `instances.removed`                             |
| `A > stock`, `F` мало    | Свободные удаляются все, затем приз изымается у владельцев — начиная с последних по времени выдачи                                        | `instances.removed`, `demoted`                  |
| `stock = 0`              | Свободные уходят, все выданные помечаются к изъятию; позиция сохраняется                                                                  | `instances.removed`, `demoted`                  |
| Позиции нет в плане      | `is_removed = true` (видимость от клиента не трогается), свободные удаляются, выданные помечаются к изъятию                               | `types.removed`, `instances.removed`, `demoted` |
| Позиция вернулась в план | `is_removed` снимается, дальше правило дефицита                                                                                           | `types.restored`, `instances.restored`          |

Выданные экземпляры не удаляются никогда. План ниже числа выданных не «недобор», а изъятие: приз у последнего получателя помечается `removing`. У владельца, получившего приз раньше, он остаётся.

**Инвариант:** синхронизация физически удаляет только свободные экземпляры со статусом `active`. Помеченные к изъятию не удаляются, даже если владельца у них уже нет. Такой бесхозный `removing` не выдаётся участникам, а при возврате плана восстанавливается последним.

`stock = 0` — законное значение: экземпляров в пуле не остаётся, позиция сохраняется. Позиции без `code` (заведённые в админке) синхронизация не трогает.

**Разбор плана:**

- `code` и `title` обязательны, `code` уникален внутри пакета; дубликат — отказ.
- Любая битая строка отклоняет весь пакет (`422 VALIDATION_ERROR` с номером позиции и причиной).
- Потолок пакета — 5000 позиций, потолок плана на позицию — 100 000 экземпляров.
- Пакет применяется одной транзакцией: обрыв не оставляет каталог в полусостоянии.

**Идемпотентность:** повторный запрос без изменений даёт нули во всех счётчиках (в разборе остаётся только `kept`). Смена подписанной ссылки на картинку изменением позиции не считается.

**Ответ (`data`):**

```json
{
  "added": 120,
  "updated": 1,
  "removed": 5,
  "types": { "added": 2, "updated": 1, "removed": 0, "restored": 0 },
  "instances": {
    "created": 120,
    "removed": 5,
    "kept": 40,
    "demoted": 0,
    "restored": 0
  }
}
```

| Поле                 | Тип | Описание                                                                             |
| -------------------- | --- | ------------------------------------------------------------------------------------ |
| `added`              | int | Сводка для клиента: экземпляров вошло в пул (= `created` + `restored`)               |
| `updated`            | int | Сводка для клиента: изменённых существующих позиций; одна позиция считается один раз |
| `removed`            | int | Сводка для клиента: экземпляров вышло из пула (= `removed` + `demoted`)              |
| `types.added`        | int | Заведено позиций каталога                                                            |
| `types.updated`      | int | Изменено позиций (атрибуты, включая видимость)                                       |
| `types.removed`      | int | Снято позиций: их нет в плане (`is_removed = true`)                                  |
| `types.restored`     | int | Позиций вернулось в план (`is_removed` снят)                                         |
| `instances.created`  | int | Создано свободных экземпляров                                                        |
| `instances.removed`  | int | Удалено свободных экземпляров                                                        |
| `instances.kept`     | int | Экземпляров осталось как было                                                        |
| `instances.demoted`  | int | Помечено к изъятию (`active` → `removing`)                                           |
| `instances.restored` | int | Возвращено в пул (`removing` → `active`)                                             |

Три плоских числа клиент складывает в свою сводку синхронизации; развёрнутая структура — для человека.

**Картинки.** `image` приходит подписанной ссылкой на файл у клиента: она живёт ограниченное время и меняется при каждой синхронизации, поэтому в ответах API её не отдают. Ссылка сохраняется в `prize_catalog.image_source_url`, а файл забирает себе отдельный проход — команда `app:prize:images` (крон, раз в час). Если содержимое не изменилось, адрес остаётся прежним. До первого прогона команды `image` у новой позиции равен `null`.

**Ошибки:**

| Ситуация                                                                                                                                   | Код                | HTTP |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------ | ---- |
| `prizes` не передан, пуст или не массив                                                                                                    | `INVALID_SYNTAX`   | 400  |
| Больше 5000 позиций в пакете                                                                                                               | `INVALID_SYNTAX`   | 400  |
| Битая позиция: нет `code`/`title`/`stock`, дубликат `code`, отрицательный или слишком большой `stock`, нечисловое число, нелогический флаг | `VALIDATION_ERROR` | 422  |

Обратный канал (сколько выдано на инстансе → клиенту) не сделан.

## 8.9. `GET /api/v1/crm/raffles/[id]/chances` — шансы под условиями розыгрыша

**Назначение:** шансы, подпадающие под условия конкретного розыгрыша. Используется для предпросмотра выборки до бронирования.

**Запрос:** `id` (path, UUID), `page`, `limit`.

**Ответ (`data.items[]`):** `chance_id`, `user_id`, `received_at`, `source_type`.

## 8.10. `GET /api/v1/crm/raffles/[id]/chances/count` — количество шансов

**Назначение:** количество шансов, подпадающих под условия розыгрыша. Используется при создании розыгрыша для мгновенного отображения размера выборки.

**Запрос:** `id` (path, UUID).

**Ответ (`data`):** `raffle_id` (UUID), `count` (int).

## 8.11. `POST /api/v1/crm/raffles/[id]/chances/winners` — установить победителей

**Назначение:** приём результатов розыгрыша от исполнительного бэкенда порциями. При последней порции (`is_last = true`) обновляет шансы, устанавливает дату проведения и переводит розыгрыш в `completed`. Обеспечивает контроль доставки порций (нумерация, проверка наличия всех порций). Вместе с результатом передаётся протокол розыгрыша.

**Запрос:**

| Параметр              | Где  | Тип    | Обяз. | Описание                                                                          |
| --------------------- | ---- | ------ | ----- | --------------------------------------------------------------------------------- |
| `id`                  | path | UUID   | да    | Идентификатор розыгрыша                                                           |
| `chunk_index`         | body | int    | да    | Номер порции                                                                      |
| `is_last`             | body | bool   | да    | Признак последней порции                                                          |
| `winners[]`           | body | array  | да    | Выигрышные шансы                                                                  |
| `winners[].chance_id` | body | UUID   | да    | Идентификатор шанса                                                               |
| `winners[].payload`   | body | object | нет   | Данные приза и другие данные                                                      |
| `protocol`            | body | object | нет   | Протокол розыгрыша (может передаваться в последней порции или отдельным запросом) |

**Ответ (`data`):**

| Поле            | Тип    | Описание                                                                |
| --------------- | ------ | ----------------------------------------------------------------------- |
| `raffle_id`     | UUID   | Идентификатор                                                           |
| `chunk_index`   | int    | Обработанный номер порции                                               |
| `status`        | string | Статус обработки (`accepted`, `duplicate`, `stale`, `unknown`, `error`) |
| `raffle_status` | string | Текущий статус розыгрыша                                                |

## 8.12. `POST /api/v1/crm/raffles/[id]/booking` — забронировать розыгрыш и шансы

**Назначение:** вызывается исполнительным бэкендом после сигнала старта. Проверяет статус `draft` и наступление конца срока сбора (иначе отклоняет запрос), переводит розыгрыш в `in_progress`, фиксирует выборку шансов атрибутом с ID розыгрыша. Замораживает розыгрыш и выборку.

**Запрос:** `id` (path, UUID).

**Ответ (`data`):** `raffle_id`, `status` (`in_progress`), `booked_chances` (int).

## 8.13. `GET /api/v1/crm/raffles/[id]/booking/chances` — забронированные шансы

**Назначение:** возврат шансов, забронированных для розыгрыша. Поддерживает пагинацию. Возвращает только шансы, соответствующие условиям розыгрыша и имеющие установленный ID розыгрыша.

**Запрос:** `id` (path, UUID), `page`, `limit`.

**Ответ (`data.items[]`):** `chance_id`, `user_id`, `received_at`, `source_type`, `raffle_id`.

## 8.14. `GET /api/v1/crm/raffles/participants` — все участники

**Назначение:** пагинированный список всех участников, имеющих шансы в розыгрышах.

**Запрос:** `page`, `limit`.

## 8.15. `GET /api/v1/crm/raffles/[id]/participants` — участники розыгрыша

**Назначение:** участники конкретного розыгрыша (имеющие шансы в его выборке).

**Запрос:** `id` (path, UUID), `page`, `limit`.

**Ответ (`data.items[]`):** `user_id` (UUID), `chances_count` (int), `is_winner` (bool).

## 8.16. `PATCH /api/v1/crm/raffles/[id]/chances` — обновить статусы шансов

**Назначение:** изменение статусов шансов розыгрыша (пометка выигрышных/проигрышных, сброс).

# Раздел 9. Очереди задач

Состояния задач: `waiting`, `in_flight`, `final_success`, `final_failed`, `manual`. Модель доставки: at-least-once, идемпотентность по `task_id` + `execution_id`.

| №   | Эндпоинт                         | Назначение                            |
| --- | -------------------------------- | ------------------------------------- |
| 9.1 | `PUT /api/v1/crm/queue/claim`    | Извлечь пакет задач из очереди (FIFO) |
| 9.2 | `POST /api/v1/crm/queue/results` | Отправить результаты задач            |
| 9.3 | `GET /api/v1/crm/tasks`          | Текущая очередь задач                 |
| 9.4 | `GET /api/v1/crm/tasks/sent`     | Задачи в работе                       |
| 9.5 | `GET /api/v1/crm/tasks/results`  | Очередь результатов                   |

## 9.1. `PUT /api/v1/crm/queue/claim` — извлечь пакет задач (FIFO)

**Назначение:** пакетный запрос исполнительного бэкенда на получение задач. Атомарно переводит выбранные задачи в `in_flight`, генерирует `execution_id`, рассчитывает `expires_at`. Учитывает `available_at` и `supported_types`. Отдельный запрос, не смешивается с отправкой результатов.

**Запрос:**

| Параметр          | Где  | Тип    | Обяз. | Описание                             |
| ----------------- | ---- | ------ | ----- | ------------------------------------ |
| `worker_id`       | body | string | да    | Идентификатор воркера или экземпляра |
| `supported_types` | body | array  | да    | Поддерживаемые типы задач            |
| `max_tasks`       | body | int    | да    | Максимум задач к получению           |
| `client_version`  | body | string | нет   | Версия клиента                       |
| `request_id`      | body | string | нет   | Идентификатор запроса                |

**Ответ (`data`):**

**Поле `tasks[]`:**

| Поле             | Тип      | Описание             |
| ---------------- | -------- | -------------------- |
| `task_id`        | UUID     | Идентификатор задачи |
| `execution_id`   | UUID     | Идентификатор выдачи |
| `type`           | string   | Тип задачи           |
| `version`        | string   | Версия схемы         |
| `payload`        | object   | Данные задачи        |
| `attempt_number` | int      | Номер попытки        |
| `created_at`     | datetime | Время создания       |

**Поле `meta`:**

| Поле                       | Тип      | Описание                                  |
| -------------------------- | -------- | ----------------------------------------- |
| `has_more`                 | bool     | Есть ли ещё задачи в очереди              |
| `next_claim_delay_seconds` | int      | Рекомендация по паузе до следующего claim |
| `throttled`                | bool     | Признак необходимости ограничить выдачу   |
| `server_time`              | datetime | Время сервера промо-инстанса              |

## 9.2. `POST /api/v1/crm/queue/results` — отправить результаты задач

**Назначение:** пакетная отправка результатов выполнения задач из исполнительного бэкенда. Для каждого результата проверяется существование задачи, состояние, совпадение `execution_id`. Применяется с учётом идемпотентности.

**Запрос:**

| Параметр                        | Где  | Тип    | Обяз. | Описание                                          |
| ------------------------------- | ---- | ------ | ----- | ------------------------------------------------- |
| `worker_id`                     | body | string | да    | Идентификатор воркера                             |
| `results[]`                     | body | array  | да    | Массив результатов                                |
| `results[].task_id`             | body | UUID   | да    | Идентификатор задачи                              |
| `results[].execution_id`        | body | UUID   | да    | Идентификатор выдачи                              |
| `results[].outcome`             | body | string | да    | `success` / `retryable_failure` / `fatal_failure` |
| `results[].result_data`         | body | object | нет   | Данные результата                                 |
| `results[].error_code`          | body | string | нет   | Код ошибки                                        |
| `results[].error_message`       | body | string | нет   | Сообщение ошибки                                  |
| `results[].retry_after_seconds` | body | int    | нет   | Задержка повтора                                  |

**Ответ (`data`):**

| Поле                | Тип          | Описание                                                 |
| ------------------- | ------------ | -------------------------------------------------------- |
| `results[]`         | array        | Обработанные результаты                                  |
| `results[].task_id` | UUID         | Идентификатор задачи                                     |
| `results[].status`  | string       | `accepted` / `duplicate` / `stale` / `unknown` / `error` |
| `results[].message` | string\|null | Пояснение                                                |

## 9.3. `GET /api/v1/crm/tasks` — текущая очередь задач

**Назначение:** пагинированный список задач в состоянии `waiting` для мониторинга.

**Запрос:** `page`, `limit`, `type` (фильтр по типу).

**Ответ (`data.items[]`):** `task_id`, `type`, `version`, `attempts` (int), `available_at`, `created_at`.

## 9.4. `GET /api/v1/crm/tasks/sent` — задачи в работе

**Назначение:** пагинированный список задач в состоянии `in_flight` (выданных и ожидающих результата) для мониторинга.

**Запрос:** `page`, `limit`, `type` (фильтр по типу).

**Ответ (`data.items[]`):** `task_id`, `type`, `execution_id`, `attempt_number` (int), `sent_at`, `expires_at`.

## 9.5. `GET /api/v1/crm/tasks/results` — очередь результатов

**Назначение:** пагинированный список результатов задач (финальный след) для мониторинга и аудита.

**Запрос:** `page`, `limit`, `type` (фильтр по типу), `status` (`success` / `failed` / `manual`).

**Ответ (`data.items[]`):** `task_id`, `type`, `status`, `result_summary` (string\|null), `completed_at`.
