# ТЗ: Панель управления

## Часть 4. Эндпоинты управляющего бэкенда

Подробное описание эндпоинтов управляющего бэкенда по функциональным областям, зафиксированным в Части 2. Управляющий бэкенд — источник правды для конфигурации; управление ведётся средствами Битрикс, поставка данных в инстансы — инициатива управляющего бэкенда.

---

## 1. Общие соглашения

### 1.1. Аутентификация

Панель управления работает с управляющим бэкендом через пользовательскую сессию администратора. Аутентификация идёт через источник пользователей.

| Аспект                             | Значение                                      |
| ---------------------------------- | --------------------------------------------- |
| Источник пользователей             | Битрикс                                       |
| Валидация учётных данных           | Выполняется Битрикс                           |
| Выдача токенов                     | Выполняется Битрикс                           |
| Хранение токенов                   | `httpOnly`-куки                               |
| Валидация токена на стороне панели | Локальная проверка подписи через общий секрет |

**Состав токенов:**

| Токен           | Назначение                                        | Время жизни            |
| --------------- | ------------------------------------------------- | ---------------------- |
| `access_token`  | Подтверждение активной сессии                     | 900 секунд (15 минут)  |
| `refresh_token` | Получение новой пары токенов без повторного входа | 604800 секунд (7 дней) |
| `user_data`     | Данные пользователя для интерфейса                | 604800 секунд (7 дней) |

**Эндпоинты аутентификации панели:**

| Эндпоинт            | Метод | Назначение                                                        |
| ------------------- | ----- | ----------------------------------------------------------------- |
| `/api/auth/login`   | POST  | Вход: принимает логин/пароль, устанавливает куки                  |
| `/api/auth/refresh` | POST  | Обновление токенов (вызывается промежуточным слоем, не браузером) |
| `/api/auth/logout`  | POST  | Выход: удаляет куки, уведомляет источник пользователей            |

**Ключевые принципы:**

- Все запросы к источнику пользователей идут только с сервера панели, никогда из браузера.
- Токены хранятся в `httpOnly`-куки.
- Данные пользователя для интерфейса читаются на сервере, чтобы исключить мигание меню.

### 1.2. Два типа управления

Управляющий бэкенд предоставляет два типа управления:

| Тип                        | Механизм                                 | Функциональные области                                      |
| -------------------------- | ---------------------------------------- | ----------------------------------------------------------- |
| Управление через интерфейс | Формы, списки, импорт средствами Битрикс | Кампании и инстансы, настройки логики, справочники, ресурсы |
| Управление через эндпоинты | Отдельные эндпоинты помимо интерфейса    | Пулы призов, синхронизация конфигурации, розыгрыши          |

### 1.3. Конверт ответов

| Тип            | Формат                                    |
| -------------- | ----------------------------------------- |
| Успех          | `{"status":"ok","data":{...}}`            |
| Ошибка         | `{"error":{"code","message","details?"}}` |
| Имена полей    | `snake_case`                              |
| Идентификаторы | UUID                                      |
| Даты           | ISO 8601                                  |

### 1.4. Поставка данных в инстансы

Управляющий бэкенд поставляет данные в инстансы двумя способами:

| Способ               | Когда срабатывает                 | Кто инициирует             |
| -------------------- | --------------------------------- | -------------------------- |
| По событию изменения | При сохранении управляемых данных | Система автоматически      |
| По эндпоинту         | По явному запросу администратора  | Администратор через панель |

## 2. Управление кампаниями и инстансами

**Назначение:** регистрация инстансов, привязка к кампаниям, управление активностью, просмотр состояния синхронизации.

**Механизм управления:** через интерфейс Битрикс (формы, списки). Отдельных эндпоинтов нет.

### 2.1. Параметры инстансов

Промо-инстансы регистрируются в управляющем бэкенде и привязываются к кампаниям. Для каждого инстанса хранятся параметры, необходимые для поставки конфигурации.

| Параметр           | Тип          | Обязательный | Описание                                                |
| ------------------ | ------------ | ------------ | ------------------------------------------------------- |
| `id`               | UUID         | да (авто)    | Уникальный идентификатор инстанса                       |
| `campaign_id`      | UUID         | да           | Принадлежность к кампании                               |
| `name`             | string       | да           | Человекочитаемое название                               |
| `base_url`         | string (URL) | да           | Базовый URL инстанса, куда слать запросы                |
| `is_active`        | boolean      | да           | Активен ли инстанс; при `false` поставка не выполняется |
| `last_sync_at`     | datetime     | нет (авто)   | Время последней успешной синхронизации                  |
| `last_sync_status` | enum         | нет (авто)   | `success`, `failed`, `in_progress`, `never`             |
| `last_sync_error`  | string       | нет (авто)   | Текст последней ошибки синхронизации                    |

### 2.2. Действия администратора

| Действие                         | Механизм          |
| -------------------------------- | ----------------- |
| Просмотр списка кампаний         | Интерфейс Битрикс |
| Просмотр инстансов кампании      | Интерфейс Битрикс |
| Регистрация инстанса             | Интерфейс Битрикс |
| Управление активностью инстанса  | Интерфейс Битрикс |
| Просмотр состояния синхронизации | Интерфейс Битрикс |

## 3. Управление настройками логики

**Назначение:** редактирование настроек кампании, авторизации, розыгрышей.

**Механизм управления:** через формы Битрикс. Настройки логики управляются через форму настроек кампании/инстанса в интерфейсе Битрикс. Отдельных эндпоинтов нет.

### 3.1. Группы настроек и ключи

Настройки логики сгруппированы по разделам.

**Группа «Кампания»:**

| Параметр              | Тип      | По умолчанию    | Описание             |
| --------------------- | -------- | --------------- | -------------------- |
| `campaign_name`       | string   | —               | Название кампании    |
| `campaign_start_date` | datetime | —               | Дата начала акции    |
| `campaign_end_date`   | datetime | —               | Дата окончания акции |
| `site_timezone`       | string   | `Europe/Moscow` | Часовой пояс сайта   |

**Группа «Регистрация и авторизация»:**

| Параметр                        | Тип | По умолчанию | Описание                       |
| ------------------------------- | --- | ------------ | ------------------------------ |
| `verification_code_ttl_minutes` | int | 15           | TTL кода подтверждения, минут  |
| `max_verification_attempts`     | int | 5            | Максимум попыток ввода кода    |
| `block_duration_minutes`        | int | 30           | Длительность блокировки, минут |
| `access_token_ttl_minutes`      | int | 15           | TTL токена доступа, минут      |
| `refresh_token_ttl_days`        | int | 30           | TTL токена обновления, дней    |

**Группа «Розыгрыши»:**

| Параметр                     | Тип                    | По умолчанию | Описание                                        |
| ---------------------------- | ---------------------- | ------------ | ----------------------------------------------- |

**Примечание:** идентификатор кампании (`campaign_id`) хранит управляющий бэкенд, инстансу он не нужен. Группа настроек продукта не поставляется на инстанс.

### 3.2. Действия администратора

| Действие                            | Механизм      |
| ----------------------------------- | ------------- |
| Редактирование настроек кампании    | Форма Битрикс |
| Редактирование настроек авторизации | Форма Битрикс |
| Редактирование настроек розыгрышей  | Форма Битрикс |

## 5. Управление пулами призов

**Назначение:** ведение пула призов на управляющем бэкенде. Пул призов — все возможные призы, где каждая запись — один реальный приз.

**Механизм управления:** для пулов призов управляющий бэкенд предоставляет отдельные эндпоинты помимо интерфейса Битрикс.

### 5.1. Эндпоинты справочника призов

| Эндпоинт                          | Метод  | Назначение                 |
| --------------------------------- | ------ | -------------------------- |
| `/api/v1/directory/prizes`        | GET    | Получить справочник призов |
| `/api/v1/directory/prizes`        | POST   | Добавить приз              |
| `/api/v1/directory/prizes/import` | POST   | Импорт призов из файла     |
| `/api/v1/directory/prizes/[id]`   | PATCH  | Изменить приз              |
| `/api/v1/directory/prizes/[id]`   | DELETE | Удалить приз               |

### 5.2. `GET /api/v1/directory/prizes` — получить справочник призов

**Назначение:** пагинированный список призов в пуле.

**Запрос:** параметры пагинации и фильтрации (по статусу, по типу).

**Ответ (`data.items[]`):** поля записи приза (`code`, `title`, `price`, `act_required`, `image`, `is_active`).

### 5.3. `POST /api/v1/directory/prizes` — добавить приз

**Назначение:** добавление приза в пул.

**Запрос:**

| Параметр       | Где  | Тип     | Обяз. | Описание           |
| -------------- | ---- | ------- | ----- | ------------------ |
| `code`         | body | string  | да    | Код приза          |
| `title`        | body | string  | да    | Название приза     |
| `price`        | body | int     | да    | Стоимость в баллах |
| `act_required` | body | boolean | да    | Требуется ли акт   |
| `image`        | body | string  | нет   | Изображение        |
| `is_active`    | body | boolean | да    | Признак активности |

**Ответ (`data`):** идентификатор созданного приза.

### 5.4. `POST /api/v1/directory/prizes/import` — импорт призов из файла

**Назначение:** массовая загрузка призов из файла. Пакетная операция.

**Запрос:** файл с данными призов (формат определяется реализацией).

**Ответ (`data`):** сводка импорта — добавлено, пропущено, ошибки.

### 5.5. `PATCH /api/v1/directory/prizes/[id]` — изменить приз

**Назначение:** частичное обновление записи приза.

**Запрос:**

| Параметр   | Где  | Тип  | Обяз. | Описание            |
| ---------- | ---- | ---- | ----- | ------------------- |
| `id`       | path | UUID | да    | Идентификатор приза |
| Поля приза | body | —    | нет   | Обновляемые поля    |

**Ответ (`data`):** обновлённые поля приза.

### 5.6. `DELETE /api/v1/directory/prizes/[id]` — удалить приз

**Назначение:** удаление записи приза из пула.

**Запрос:**

| Параметр | Где  | Тип  | Обяз. | Описание            |
| -------- | ---- | ---- | ----- | ------------------- |
| `id`     | path | UUID | да    | Идентификатор приза |

**Ответ (`data`):** признак удаления.

## 6. Управление ресурсами (контентом)

**Назначение:** ведение контента для фронтенда инстанса. Управление файлами и контентом ведётся средствами Битрикс.

**Механизм управления:** через Битрикс как источник правды для контента. Отдельных эндпоинтов для управления ресурсами нет.

### 6.1. Модель данных ресурсов

Каждый ресурс на управляющем бэкенде описывается записью:

| Поле          | Тип        | Обязательный | Описание                                                          |
| ------------- | ---------- | ------------ | ----------------------------------------------------------------- |
| `key`         | string     | да           | Ключ ресурса — уникальный идентификатор                           |
| `type`        | enum       | да           | Тип ресурса: `text`, `image`, `json`, `document`, `file`          |
| `value`       | string     | да           | Значение: текст, ссылка на файл в Битрикс, JSON-строка            |
| `scope`       | enum       | да           | Уровень разграничения: `global`, `campaign`, `instance`           |
| `campaign_id` | UUID\|null | условно      | Привязка к кампании (для `scope = campaign` и `scope = instance`) |
| `instance_id` | UUID\|null | условно      | Привязка к инстансу (для `scope = instance`)                      |
| `is_active`   | boolean    | да           | Признак активности                                                |
| `updated_at`  | datetime   | да           | Время последнего обновления                                       |

### 6.2. Типы ресурсов и их значения

| Тип        | Описание                 | Значение на бэкенде      | Значение на инстансе                |
| ---------- | ------------------------ | ------------------------ | ----------------------------------- |
| `text`     | Текст или HTML           | Текст                    | Текст (без изменений)               |
| `image`    | Изображение              | Ссылка на файл в Битрикс | Путь на инстансе (после скачивания) |
| `json`     | Структурированные данные | JSON-строка              | JSON-строка (без изменений)         |
| `document` | Документ для просмотра   | Ссылка на файл в Битрикс | Путь на инстансе (после скачивания) |
| `file`     | Файл для скачивания      | Ссылка на файл в Битрикс | Путь на инстансе (после скачивания) |

### 6.3. Уровни разграничения ресурсов

| Уровень    | Описание                     |
| ---------- | ---------------------------- |
| `global`   | Общедоступные ресурсы        |
| `campaign` | Ресурсы кампании             |
| `instance` | Ресурсы конкретного инстанса |

**Разрешение конфликтов:** более специфичный уровень переопределяет более общий (инстанс > кампания > глобальный). Инстанс получает плоский список без пометок об уровне.

### 6.4. Действия администратора

| Действие                              | Механизм          |
| ------------------------------------- | ----------------- |
| Управление текстовыми ресурсами       | Интерфейс Битрикс |
| Управление изображениями              | Интерфейс Битрикс |
| Управление структурированными данными | Интерфейс Битрикс |
| Управление документами и файлами      | Интерфейс Битрикс |
| Разграничение по уровням              | Интерфейс Битрикс |

## 7. Синхронизация конфигурации

**Назначение:** принудительная синхронизация конфигурации во все активные инстансы кампании. Используется для принудительной синхронизации после массовых изменений, повторной синхронизации после сбоев, сверки данных.

**Механизм управления:** отдельный эндпоинт.

### 7.1. `POST /api/v1/camps/[id]/sync` — запустить синхронизацию

**Назначение:** запустить полную синхронизацию конфигурации во все активные инстансы кампании.

**Авторизация:** администраторская (через интерфейс Битрикс).

**Запрос:**

| Параметр      | Где   | Тип  | Обяз. | Описание                                                               |
| ------------- | ----- | ---- | ----- | ---------------------------------------------------------------------- |
| `id`          | path  | UUID | да    | Идентификатор кампании                                                 |
| `instance_id` | query | UUID | нет   | Если указан — синхронизировать только этот инстанс; иначе все активные |

**Ответ (`data`):**

| Поле                    | Тип          | Описание                                            |
| ----------------------- | ------------ | --------------------------------------------------- |
| `campaign_id`           | UUID         | Идентификатор кампании                              |
| `syncs[]`               | array        | Массив результатов по каждому инстансу              |
| `syncs[].instance_id`   | UUID         | Идентификатор инстанса                              |
| `syncs[].instance_name` | string       | Название инстанса                                   |
| `syncs[].status`        | enum         | `success`, `failed`, `skipped`                      |
| `syncs[].settings`      | object       | Сводка по настройкам: `{updated, rejected}`         |
| `syncs[].dictionaries`  | object       | Сводка по справочникам: `{added, updated, removed}` |
| `syncs[].error`         | string\|null | Текст ошибки при `status = failed`                  |
| `syncs[].duration_ms`   | int          | Длительность синхронизации в миллисекундах          |

**Логика обработки:**

| Шаг | Действие                                                                                                                   |
| --- | -------------------------------------------------------------------------------------------------------------------------- |
| 1   | Проверка существования кампании                                                                                            |
| 2   | Получение списка активных инстансов кампании (или одного, если указан `instance_id`)                                       |
| 3   | Для каждого инстанса — выполнение полной синхронизации: настройки (частичное обновление), справочники (синхронизация пула) |
| 4   | Формирование сводки по каждому инстансу                                                                                    |
| 5   | Обновление `last_sync_at`, `last_sync_status`, `last_sync_error` для каждого инстанса                                      |
| 6   | Возврат общей сводки                                                                                                       |

### 7.2. Триггеры синхронизации

Синхронизация запускается одним из триггеров:

| Триггер              | Когда срабатывает                 | Кто инициирует             |
| -------------------- | --------------------------------- | -------------------------- |
| По событию изменения | При сохранении управляемых данных | Система автоматически      |
| По расписанию        | Периодическая полная сверка       | Система автоматически      |
| Вручную              | По явному запросу администратора  | Администратор через панель |

Все три триггера запускают один и тот же процесс синхронизации. Разница только в причине запуска, не в механике.

## 8. Запуск розыгрышей

**Назначение:** запуск процесса розыгрыша на исполняющем бэкенде.

**Механизм управления:** отдельный эндпоинт.

### 8.1. `POST api/v1/raffle/run` — провести розыгрыш

**Назначение:** запустить процесс розыгрыша. Вызывается при нажатии администратором кнопки старта в интерфейсе панели. Запрос строго контролируется от повторного и множественного нажатия.

**Запрос:** запрос содержит заданные параметры розыгрыша.

**Последовательность после запуска** (выполняется исполняющим бэкендом, панель только мониторит):

| Шаг | Действие                                | Эндпоинт на инстансе                              |
| --- | --------------------------------------- | ------------------------------------------------- |
| 1   | Получение параметров выборки с инстанса | `GET api/v1/crm/raffles/[id]`                     |
| 2   | Бронирование розыгрыша и шансов         | `POST api/v1/crm/raffles/[id]/booking`            |
| 3   | Забор шансов                            | `GET api/v1/crm/raffles/[id]/booking/chances`     |
| 4   | Выполнение алгоритма розыгрыша          | Внутренняя логика                                 |
| 5   | Отправка победителей порциями           | `POST api/v1/crm/raffles/[id]/chances/winners`    |
| 6   | Передача протокола розыгрыша            | В составе последней порции или отдельным запросом |

**Примечание:** этот запрос строго контролируется от повторного и множественного нажатия. Повторный запрос с тем же розыгрышем отклоняется.

## 9. Мониторинг проведения розыгрышей

**Назначение:** отслеживание процесса проведения розыгрышей на исполняющем бэкенде.

**Механизм управления:** отдельные эндпоинты.

### 9.1. `GET api/v1/raffles` — список проводимых розыгрышей

**Назначение:** список всех розыгрышей, которые в данный момент проводятся на исполняющем бэкенде. Используется для мониторинга.

**Запрос:** параметры пагинации и фильтрации (по статусу проведения).

**Ответ (`data.items[]`):** идентификатор розыгрыша, идентификатор инстанса, статус проведения, время старта.

### 9.2. `GET api/v1/raffle/[id]` — статус проведения розыгрыша

**Назначение:** статус проведения конкретного розыгрыша. Используется для мониторинга процесса.

**Запрос:**

| Параметр | Где  | Тип  | Обяз. | Описание                |
| -------- | ---- | ---- | ----- | ----------------------- |
| `id`     | path | UUID | да    | Идентификатор розыгрыша |

**Ответ (`data`):** идентификатор розыгрыша, статус проведения, этап обработки, время старта, время завершения (если завершён), ошибки (если есть).

## 11. Ключевые принципы

| Принцип                             | Содержание                                                                                                             |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Источник правды                     | Управляющий бэкенд — единственное место создания и изменения конфигурации. Ручное редактирование на инстансе запрещено |
| Одна кампания — несколько инстансов | Кампания является высокоуровневой сущностью и может содержать несколько инстансов                                      |
| Инстанс не знает о других           | Инстанс не знает об управляющем бэкенде, о кампании, о других инстансах. Он только принимает переданные ему данные     |
| Инстанс не инициирует               | Поставка конфигурации — инициатива управляющего бэкенда                                                                |
| Разделение управления               | Настройки и справочники — через Битрикс; пулы призов, синхронизация, розыгрыши — через эндпоинты                       |
| Версионирование обмена              | Каждый запрос к инстансу несёт заголовок версии формата обмена                                                         |
